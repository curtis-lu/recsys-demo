# pipeline 的檢查：分幾層、各擋什麼、哪些擋不住

這頁給改設定檔、跑 pipeline 的人。讀完應該知道三件事：一個錯誤大概會在什麼時候被擋下、為什麼在那裡，以及哪幾種錯誤**不會**被擋。

這頁不逐條列出每一個檢查。被擋下來時要改哪裡，看錯誤訊息。訊息裡帶代號的（例如 `A24`），完整定義在 `src/recsys_tfb/core/consistency.py` 開頭的說明。

## 原則：需要看到什麼，就放在看得到它的最早時間點

一個檢查放在哪裡，取決於它要看到什麼才判斷得出對錯：

| 要看到什麼 | 最早什麼時候看得到 |
|---|---|
| 設定檔、指令參數 | 指令一開始，還沒讀任何資料 |
| 資料 | 讀到那份資料的時候 |
| 這次做出來的結果 | 結果做出來之後 |

放得越晚，被擋下之前白跑的就越多。例如 `training.final_model_strategy` 決定超參數搜尋（HPO）結束後怎麼產出最終模型；如果等到用它的那一步才檢查，這個值打錯字，要整個搜尋跑完才會發現。所以它在指令一開始就查（`A25`）。

## 三層

```
python -m recsys_tfb <指令> --env <env>
│
├─ ① 開跑前：看設定檔和指令參數
│
├─ ② 讀資料時：看資料的長相
│
└─ ③ 交出去前：看這次做出來的結果
```

### ① 開跑前：看設定檔和指令參數

**擋什麼**：設定自相矛盾、值不合法、打錯字。

**例子**：同一個月同時寫在 `dataset.train_snap_dates` 和 `dataset.test_snap_dates` 裡，跑 dataset 時會被擋下（`A24`）。拿同一個月訓練又拿它評估，評估數字會好看得不真實。

**什麼時候**：讀完設定檔、還沒啟動 Spark。所有指令都會先過這一層，包括四個 source ETL 指令（`feature_etl`、`label_etl`、`sample_pool_etl`、`inference_population_etl`）。

這一層分兩批：

- **每個指令都查的**：`--env` 指的設定資料夾在不在（`A30`）、`schema` 的格式，以及大部分設定之間的矛盾。這一批不分指令，連只有 training 或 evaluation 才用到的設定也在裡面。所以**別的 pipeline 的設定打錯，也會擋住你現在跑的指令**。
- **只在某個指令查的**：少數只有一條 pipeline 會讀的設定，例如 `inference.entity_buckets` 設成 0（`A27`，只在 inference 查）；以及只有某些指令才有的旗標，例如 `--rebuild-dates` 寫了設定裡沒有的月份（`A21`）。

**例外**：指令參數**指到的東西**不存在，要等 Spark 啟動之後才查到。例如 `--model-version` 指的模型版本沒有訓練過，或 `--from-node` 寫的步驟名稱打錯。

### ② 讀資料時：看資料的長相

**擋什麼**，兩種：

- **資料跟設定對不上**。例：設定沒把某一欄宣告成類別欄，資料裡它卻是文字（`B6`）。放著不管，training 讀資料時會失敗。
- **拿舊的東西當新的**。例：evaluation 要沿用上一輪算好的指標，但那份指標是用另一份設定算的，就會擋下來，並告訴你從哪一步重跑。

**什麼時候**：

- **dataset** 有三個**資料閘**：專門檢查、本身不改資料的步驟。
  - 開頭：來源表出現的 item 值、特徵欄的型別、各欄的用途，跟設定對不對得上（`B1`、`B5`、`B6`、`B7`）。
  - 特徵編碼完：整數、decimal 這類值有固定間距的欄位，轉成宣告的儲存型別時，會不會讓兩個不同的值變成同一個（`B8`）。
  - 最後：train、train_dev、calibration 的 model_input 組好之後，列數是否等於組它用的 key 表（每一列是一筆抽到的候選）。列數變多，代表來源表有重複的 join 鍵（`B10`）。

  它們都盡量少讀：型別只讀表的欄位定義，後兩個只讀 parquet 檔尾的統計；只有開頭那個要實際讀 `sample_pool` 與 `label_table`，取出設定月份裡出現過哪些 item。
- **training** 在讀訓練資料之前，再查一次特徵欄是不是數字（`B6`），並查它存成的型別是不是設定宣告的那個（`B9`）。舊版 dataset 建出來的資料不會重過 dataset 的資料閘，這一步是補救。
- **inference、evaluation** 在讀到那份資料的那一步裡查。

### ③ 交出去前：看這次做出來的結果

**擋什麼**：結果本身不完整，卻要交給下游。

**例子**：inference 發布排名之前，查每個 query group 是不是都排滿了全部 item、該有的分區有沒有都寫出來。沒通過就不發布。

**什麼時候**：結果做出來之後、寫進下游讀的表之前。

### 四個 source ETL 指令

它們產出的是其他 pipeline 讀的來源表，除了 ① 之外，檢查的時間點跟上面不一樣：

- **寫之前查上游**（`source_checks`：分區在不在、列數夠不夠、欄位有沒有變）：**只有帶 `--source-check` 時才跑**，而且那一次只檢查、不寫表。
- **寫完才查輸出**（`quality_checks`：列數、主鍵重複或空值、空值比例）：表已經寫進去之後才查。沒通過會中止後面的表，但**不會撤回已經寫進去的那一張**。沒設定 `quality_checks` 的表，不查資料的值。

## 三件擋不住的事

**1. 用 `--from-node`／`--only-node` 跳過的步驟，裡面的檢查不會跑。**
dataset 的三個資料閘都在此列；就算切片自動補跑了前面的步驟，後面的資料閘也不會跟著補跑。執行計畫（`[plan]` 開頭的那幾行）會列出被跳過的步驟。上一輪跑完之後來源表如果變過，這一輪不會發現。① 開跑前的檢查不受影響，每次都會跑。

**2. 已經做好的產物會被直接沿用，框架不保證它是用現在的設定、程式、資料做的。**
框架決定沿用還是重做，看的是產物在不在，以及一個版本號。版本號只由一部分設定和 `feature_table` 的欄位結構算出來。所以下面這些情況，舊產物照樣被沿用：

- 改了程式。
- 來源表的某個月被回補過。
- 改了不進版本號的設定，例如 `inference.*` 底下的設定：已經寫出的評分分區不會重算，除非帶 `--rebuild-dates`。
- 改了上游的設定，卻沒有重跑上游：training 預設用最新一版 dataset，inference 和 evaluation 預設用 promote 過的模型，都不會發現上游的設定已經不一樣。

什麼時候會出事、怎麼強制重算，見 [`pipeline-slicing.md`](pipeline-slicing.md) 的〈接續前提〉。

**3. 設定「合法」不等於「正確」。**
檢查只能發現設定自相矛盾或值超出範圍。一個合法但填錯的值不會被擋，例如抽樣比例該填 `0.1` 卻填了 `0.01`。
