## 1. 結論先講

**這條 pipeline 沒有被寫壞，也沒有明顯的工程脂肪。** 生產一輪約 2.4 小時（外推，
見 §9 的距離），其中 **98% 是 `lgb.train` 那 20 次呼叫**。所有 Python 側的東西——
快取、預測、算 mAP、SHAP、診斷、MLflow——加起來不到 2%。

**本輪提出七個優化假設，七個全部被自己的實驗或一句話的查證否決**（§7）。這不是
失敗的一輪：它把「該往哪裡看」收斂到一個很小的範圍，並且留下七條「這裡不用再看」
的紀錄。

剩下真正能動的，依「要付什麼代價」分三類：

| 機會 | 省多少 | 代價 | 證據 |
|---|---|---|---|
| 4 核 → 16 核 | **1.35–1.75×**（2.43h → 1.4–1.8h） | 要資源，不改任何 code | 實測 1/2/4/8 核，Amdahl 擬合外推 |
| `max_bin` 255 → 63 | −12.5% | **會改模型**，要驗準確度 | 消融實測，區間不重疊 |
| 每輪評估 `train_dev` 的頻率 | −4.3% | 不改模型 | 消融實測，4/4 輪一致 |
| `compute_metrics_uncalibrated` | −0.24% | 不改模型 | 推導＋實測（見 §6.1） |

**最大的那一條不在程式碼裡。** 而且它也只有 1.4–1.8 倍——就算給無限多核心，
Amdahl 天花板也只讓 2.43 小時降到 1.0–1.5 小時（§5.2）。

**最重要的結構事實**：`lgb.train` 裡影響最大的三個因子（`num_leaves` −38%、
`feature_fraction` +18%、`bagging_fraction` +4%）**全部在 HPO 的搜尋空間裡**。它們的
值是 HPO 為了 mAP 選的，不能為了速度去釘——那不是優化，那是搶 HPO 的工作。這一條
決定了本輪能動的範圍為什麼這麼小。

## 2. 從排序語意推：training 的必要工作是什麼

**這一節先寫，因為它決定了後面所有數字該怎麼讀**（規則 1）。不先確定「什麼是
必要的」，從執行剖面往上推只會推出「也許能省」，然後把模型必須做的工當成浪費。

### 2.1 三個「誰要求的」

| 問題 | 答案 | 所以 |
|---|---|---|
| 20 個 trial 是誰要求的？ | 人。`n_trials: 20` 是超參數搜尋的品質下限，不是實作副產物 | **trial 數不是脂肪**。能動的是「每個 trial 裡有多少輪是白跑的」 |
| 資料必須整份在記憶體裡嗎？ | 不必，而且**已經解決了** | 不是剩下的機會，見 §2.3 |
| early stopping 看的是什麼？ | train_dev 的 `binary_logloss`，不是 HPO 的評分標準 | 這是 pruning 不免費的結構原因，見 §2.4 |

### 2.2 列數受模型類別保護，欄數不受任何東西保護

這是本輪最重要的一條，其餘結論都掛在它下面。

```
列數（訓練框有幾列）
   └─ 一個 query group (time, entity) 配它的每個候選 item，一列一個候選
   └─ 這是 flat GBDT 學 entity × item 交互作用的唯一實作方式
   └─ 想縮小它 = 換模型類別 = 建模決策，不是效能工作
   → 受保護。（同 dataset 那輪 §2 的結論，此處不重複推導）

欄數（每列有幾個特徵）
   └─ 是「feature_table 剛好有幾欄」，沒有任何排序語意要求它是 665
   └─ LightGBM 每輪 boosting 的成本 ≈ O(列數 × 欄數)：每個特徵都要建直方圖
   └─ repo 已經有旋鈕：training.feature_selection.exclude
   └─ 而它現在是 []
   → 不受保護，而且工具已經在手上沒用。
```

**判斷訊號**（規則 1）：一個優化提案若講得出「這樣會少算 X」，但講不出「X 對
這個題目本來就沒有貢獻」，那是從機制往上推。砍欄數過得了這一關——665 欄裡有多少
對排序有貢獻，是可以量的（LightGBM 的 gain importance），不是猜的。
砍列數過不了——每一列都是一個候選，砍掉就是不排它。

### 2.3 「整份進記憶體」這題已經被前人解掉了，不要重新發現它

兩個機制都在現役，量測前先確認過：

- **train**：`prepare_lgb_train_inputs` 只建**一次** `lgb.Dataset` binary，20 個
  trial 共用。LightGBM 內部存的是分箱後的表示（每格約 1 byte），不是原始 float。
- **val**：`io/disk_matrix.py` 把 val 矩陣 memmap 在磁碟上，`TrialScorer` 分批走。
  這是 2026-07 那次 96 GiB OOM 之後補的（見
  [`2026-07-11-training-oom-investigation.md`](2026-07-11-training-oom-investigation.md)）。

所以「把資料搬出記憶體」不是剩下的機會。**開工前掃一眼 deferred 清單與既有機制，
別重新發現已解問題**——這條寫在這裡是因為量測初期我確實往這個方向想過。

### 2.4 為什麼 pruning 在這條 pipeline 上不是免費的

Optuna 的 pruning 需要「訓練中途的分數」來判斷這個 trial 該不該砍。但這條 pipeline 的
兩個分數是分開的：

```
LightGBM 每輪算的      : binary_logloss on train_dev   ← 免費，但不是評分標準
HPO 判 trial 好壞的    : macro_per_item_map on val     ← 是評分標準，但訓練完才算
                          （hpo_objective，conf/base/parameters_training.yaml）
```

這是刻意的設計：「一個 trial 被評判的數字，不是它的 early stopping 所優化的數字」
（`hpo_scoring.py` 的 docstring）。代價是——要用真正的評分標準做 pruning，就得在
訓練中途算 mAP，那不免費；要用免費的 logloss 做 pruning，就得先證明
**中途的 logloss 排得動最終的 mAP**。後者未經證實，見 §7。

## 3. 怎麼量的（可以重跑）


### 3.1 兩條獨立掃描，刻意不混

生產是本機的 62 倍列、29 倍欄。兩邊要比同一件東西——比的是**進 LightGBM 的訓練框**，
不是來源表：生產 `extract_Xy.X` 是 4,542,746 列 × 663 欄（2026-07 OOM log），本機
`prepare.ds_train` 是 73,337 列 × 23 欄。同時放大兩維會讓
兩個效應分不開，而它們的優化手段完全不同（§2.2）。所以：

| 掃描 | 固定 | 變動 |
|---|---|---|
| 列數 | 欄數 24 | 客戶數 1,000 → 4,000 → 16,000 |
| 欄數 | 客戶數 1,000 | 欄數 24 → 128 → 665（665 ＝ 生產實際值） |

兩端各 3 次重複、中間 1 次：斜率只用兩端，中間是用來看「兩點連線有沒有說謊」——
中點明顯偏離連線就表示冪次模型本身不適用，不是雜訊。重複次數花在兩端，因為判準是
**兩端的區間有沒有重疊**（規則 4）。執行順序刻意交錯大小規模，不讓同一規模連著跑
（連跑會讓後面那次吃到熱磁碟快取）。

### 3.2 向生產對齊的兩個設定

- `OMP_NUM_THREADS=4`：生產 driver 是 **4 核**，本機是 8 核。不釘的話量到的是雙倍算力。
  （`num_threads: 4` 本來就在 `conf/base/parameters_training.yaml`，`conf/local/` 是空的，
  所以那一項不必額外處理。）
- `TZ=Asia/Taipei`：機器時區是 `Asia/Seoul`，Spark session 設 `Asia/Taipei`，不對齊會讓
  月份過濾靜默篩出 0 列（dataset 那輪 §9.1 踩過）。

### 3.3 補欄位的做法與它的限制

`data/verification/gen_scaled.py` 把 feature_table 補到目標欄數，型別比例照生產的
`schema_types`（float 61% / int32 14% / int64 25%）。

**刻意不補 string 欄**：生產那 9 個 string 欄正是 2026-07 OOM 的兇手，但 B6 一致性閘
上線後它們會在入口被擋下——現行生產路徑不會有 object dtype 矩陣，本機補了反而量到
一條已經不存在的路徑。

**這把尺的限制**（規則 3）：補上去的是隨機雜訊欄，對模型沒有預測力。LightGBM 每輪
仍然要為每個特徵建直方圖，所以**每輪的成本**是真的；但雜訊欄會影響 early stopping
的收斂輪數，所以**總時間**混了「每輪成本」與「跑幾輪」兩件事。實測證實這不是空談：
128 欄的總時間只放大 1.65 倍（看起來 k≈0.29），但**每輪成本**放大 3.50 倍（k≈0.73）
——總輪數從 7,614 掉到 7,104 稀釋掉了差距。**§4 的斜率一律以每輪成本計**，
`total_rounds` 一起列出來讓讀者能自己還原總時間。

**第二個限制：TPE 是自適應的。** `optuna.samplers.TPESampler(seed=seed)` 在不同資料
規模下走出的搜尋路徑不同，抽到的 `num_leaves` 等參數會直接改變每輪成本。三個列數
規模的每輪成本（1.98 → 6.21 → 23.78 ms）進展乾淨、中間點落在冪次線上，所以這個混淆
看來是次要的——但它沒有被控制掉，不能宣稱斜率精確到小數第二位。

### 4.9 預先登記的預測 —— 兩個維度的效應相乘嗎？

**這一節在量之前寫**（規則 4：先寫預期再量，是防止事後合理化最便宜的手段）。

生產外推的整個地基是一個未驗證的假設：列數效應與欄數效應**相乘**。本輪的量測點是
L 形的——(大列 × 小欄) 與 (小列 × 大欄)，缺 (大列 × 大欄) 那個角。缺的正是生產所在
的那一角。

用 `tune_hyperparameters` 的兩個斜率（列 0.88、欄 0.76，基準 16.89s @ 73,337×23）：

| 點 | 列數放大 | 欄數放大 | 相乘預測 |
|---|---|---|---|
| 驗證點 4,000 客戶 × 665 欄 | 4.0× → ×3.36 | 28.8× → ×12.87 | **731s（12.2 分）** |
| 生產 4,542,746 × 663 | 61.9× → ×37.75 | 28.8× → ×12.87 | **8,204s（2.28 小時）** |

**判準**：驗證點落在 731s 的 ±30%（512–950s）→ 相乘成立，生產外推可用。
明顯低於區間 → 兩效應次相乘，生產外推要往下修。容差開到 ±30% 是因為 TPE 的搜尋
路徑在不同規模下不同（§3.3 第二個限制），斜率本身沒有小數第二位的精度。

實測結果見 §4.10。

## 5. `lgb.train` 的內部拆解（消融）

`lgb.train` 佔全 pipeline 的 98%，但那是黑盒子的量法。LightGBM 的 Python API 不分報
內部階段，發行版 wheel 也沒開編譯期的 TIMETAG 計時器。**消融是這個環境下唯一拿得到
內部分佈的方法**：關掉一個因子、看時間掉多少。

腳本：`data/verification/ablate_lgb_train.py`（73,337 × 663、100 輪、4 執行緒、
5 次交錯；rep1 為暖機輪，全體慢 2–3 倍，一律剔除）。

### 5.1 哪些旋鈕是 HPO 的，哪些是你的

| 變體 | 中位 | vs base | 改模型？ | **旋鈕歸誰** |
|---|---|---|---|---|
| `leaves_8`（`num_leaves` 32→8） | 2.74s | **−38.2%** | 是 | **HPO**（search_space 4–64） |
| `ff_1.0`（`feature_fraction` 0.8→1.0） | 5.23s | **+17.8%** | 是 | **HPO**（search_space 0.6–1.0） |
| `no_bagging`（`bagging_freq` 1→0） | 4.61s | +4.0% | 是 | **HPO**（`subsample` 0.6–1.0） |
| `max_bin_63`（255→63） | 3.88s | **−12.5%** | 是 | 你的（conf 沒設、HPO 沒搜） |
| `no_valid`（拿掉 `valid_sets`） | 4.25s | −4.3% | 否 | 你的 |
| `col_wise`（`force_col_wise`） | 4.22s | −5.0% | 否 | 你的（但無效，見 §7.6） |
| `row_wise`（`force_row_wise`） | 5.57s | **+25.5%** | 否 | 你的（**地雷，別設**） |
| `base`（生產形狀） | 4.44s | — | — | — |

**這張表是本輪最重要的發現。** 影響最大的三個因子全部在 HPO 的搜尋空間裡——它們的
值是 HPO 為了 mAP 選的。為了速度去釘它們不是優化，是搶 HPO 的工作。**扣掉那些，
工程面能動的只剩 `max_bin`（要付準確度）與每輪評估（−4.3%）。**

消融是**診斷**，不是提案清單：`max_bin_63` 告訴你建直方圖佔多少，但把它當建議
就等於在沒有準確度證據的情況下改模型。

### 5.2 執行緒擴展性：加核心能換到多少

腳本：`data/verification/bench_thread_scaling.py`（291,030 × 663、50 輪、4 次交錯）。

| 核心 | 中位秒 | 加速比 | 平行效率 |
|---|---|---|---|
| 1 | 18.48 | 1.00× | 100% |
| 2 | 10.88 | 1.70× | 85% |
| 4 | 6.82 | 2.71× | 68% |
| 8 | 5.93 | 3.12× | **39%** |

**平行效率在 4 核之後就崩了。** 8 核只比 4 核快 15%。

Amdahl 擬合給區間，因為 8 核那點可能被機器上其他 session 壓低（§8.2）：

| | 樂觀（用 1&4 核解） | 保守（用 1&8 核解） |
|---|---|---|
| 可平行比例 p | 0.841 | 0.776 |
| 天花板 1/(1−p) | 6.3× | 4.5× |
| 4 核 → 16 核 | 1.75× → **1.39 小時** | 1.35× → **1.79 小時** |
| 4 核 → 無限核 | 2.33× → 1.05 小時 | 1.65× → 1.47 小時 |

**就算給無限多核心，也只能從 2.43 小時降到 1.0–1.5 小時。**

**一個支持樂觀端的理由**：平行效率通常隨問題變大而變好（固定開銷被攤薄）。這裡量的
是 29 萬列，生產是 454 萬列——每輪工作量多 15 倍，執行緒更不容易餓著。所以生產的 p
很可能高於 0.84。**這是可驗證的預測**：在生產機上跑一次 4 核 vs 8 核的對照就知道，
而且那直接決定「該要幾核」。

## 6. 不改模型就能拿的兩條（都很小）

### 6.1 `compute_metrics_uncalibrated`：整包重算，只為一個 MLflow 指標

`compute_test_mAP_spark` 在偵測到校準後，會把 `score_uncalibrated` 改名成 `score`
再跑**一整遍** `compute_all_metrics`。實測它佔該 node 的 42–45%。

**在現行設定下，那一遍算出來的數字必然與第一遍相同**——這條是推導，不是量測：

```
calibration.method: sigmoid
  → CalibratedModelAdapter 用 LogisticRegression 擬合一維、全域一個
  → predict = 1/(1+exp(-(w·s+b)))，w>0 時嚴格遞增
  → 組內排序完全不變
  → 而 compute_all_metrics 的每一項都是排名類（map/ndcg/precision/recall/
    hit_rate/mean_pos）或純計數（dataset_overview）
  → 兩遍必然相同
```

實測佐證：log 印的 `calibrated=0.6575 uncalibrated=0.6575`。

而第二遍算出來的東西**只有一個被用到**——MLflow 的 `uncalibrated_overall_map`
（`experiment_log.log_calibration_outcome`）。連 `per_item_map_attr` 都算了沒人用。

**修法要綁在設定上，不能寫成通則**：

| `calibration.method` | 第二遍會不會給出不同數字 |
|---|---|
| `sigmoid`（現行） | 不會。嚴格單調且一對一 → 跳過，沿用第一遍 |
| `isotonic`（可選） | **會**。`IsotonicRegression` 有平坦段 → 造出同分 → 排名真的會變 → 照舊算 |
| sigmoid 在極端值飽和 | 理論上會（不同分數被壓成同一個 float）→ 這是這條的殘留風險 |

**不要動的東西**：`score_uncalibrated` **欄位**本身被下游診斷依賴，而且有測試釘住
（`test_config_shift.py::test_uses_uncalibrated_score_and_fails_loud_without_it`、
`test_item_ability.py::test_requires_uncalibrated_score`）。要拿掉的只是那一遍
**重算**，不是那個欄位。

**份量**：生產外推約 21 秒，佔整輪 0.24%。**這是真實的冗餘，修法乾淨、風險低，
但它不會改變「跑一整晚」的處境。** 而且它是 Spark node，是本輪外推最不可靠的一項
（本機 `local[*]` 單一 JVM vs 生產多 executor 叢集）。

### 6.2 每輪在 `train_dev` 上的評估：−4.3%

消融的 `no_valid` 變體，4/4 輪一致比 base 快。early stopping 需要逐輪的值，但評估
**頻率**是可調的，而且不改變長出來的樹。

**沒有往下驗證**：改成每 N 輪評估一次會讓 early stopping 的觸發點位移（`best_iteration`
會落在 N 的倍數上），那會不會影響選出來的模型，本輪沒測。−4.3% 的份量也不足以
justify 那個風險。列在這裡是為了記錄「量過了、是這個量級」。

## 7. 測過並否決的假設

**這一節跟正面結果一樣重要**（規則 9）。不寫下來，下一個人會重走一次，而且會走得
更有信心，因為「這看起來明明可行」。

### 7.1 「把 `num_threads` 開大」→ 生產只有 4 核，已經吃滿

`conf/base/parameters_training.yaml` 的 `num_threads: 4` 註解寫的是「釘定固定的 core
count，避免 LightGBM fallback 到 `OMP_NUM_THREADS=1` 或被 cgroup 限縮的 cpu_count
default」——那是一個**保底值**，不是量出來的最佳值。加上 `spark_lifecycle.release_during_hpo:
true`（HPO 期間 Spark session 被釋放，叢集閒置），看起來是「一台機器只用 4 核跑好幾
小時」的典型浪費。

**問了一句話就死了**：生產 driver 就是 4 核。`num_threads: 4` 是滿的。

這條記在這裡是因為它的**形狀**會重複出現：「設定值看起來保守」不等於「有餘裕可用」。
規則 7 說「領域通則套用到本專案前先確認本專案的實際設定」，這裡的「設定」不只是
config 鍵，也包括跑它的那台機器。

### 7.2 「砍 `n_trials`」→ 20 是搜尋下限，不是脂肪

從佔比看，HPO 是最大的一塊，所以「少試幾次」是最直接的算術。但從超參數調優的角度，
20 個 trial 本來就已經是偏少的一端——再砍就不是「用準確度換速度」，是搜不出東西。

**這條的教訓是提問的方式**：正確的切法不是「trial 數能不能砍」，而是
「**同樣 20 個 trial，能不能更便宜**」。前者把成本轉嫁給模型品質，後者才是效能工作。

### 7.3 「val 矩陣的磁碟 I/O 是瓶頸」→ 生產有 128 GB，頁快取吃得住

`TrialScorer` 每個 trial 都把整個 `X_val` 從磁碟走一遍（`_predict_in_row_batches`），
而生產的 val 矩陣是 37–89 GiB（`io/disk_matrix.py` 的估算）。20 個 trial 就是走 20 遍，
若記憶體塞不下就是真的讀 20 遍磁碟。`disk_matrix.py` 量過「predict 只佔一個 trial 的
3.3%」，但那是在矩陣塞得進記憶體時量的——**那個前提在生產成不成立，是這條的關鍵**。

**生產 driver 有 128 GB**，37–89 GiB 塞得進頁快取。這條大幅減弱。

保留一個尾巴：89 GiB + LightGBM 的分箱資料 + 其他配置，在 128 GB 上並不寬裕，
真要排除得看生產的實際 page fault 數。列為「已減弱、未完全排除」。

---

### 7.4 「用 `feature_importance` 的 gain=0 挑掉沒用的特徵」→ 循環論證

欄數是唯一不受排序語意保護的維度（§2.2），所以「砍掉沒貢獻的特徵」看起來是乾淨的
一步，而 `compute_feature_importance` 本來就在跑、`feature_selection.exclude` 旋鈕
本來就存在（現在是 `[]`）。

**使用者一句話點破**：要拿到那個檔，得先跑完一整輪 training；而 gain 又取決於那輪
HPO 選到的超參數（`colsample_bytree` 還在隨機抽 60–100% 的欄）。刪完欄位假設空間就
變了，HPO 得重跑，重跑後的 gain 又不一樣。**不是「免費讀個檔」，是「先花一整晚，
才知道要刪什麼，而且那個答案還會變」。**

**這條的教訓比結論重要**：我是用**成本斜率**挑方向，不是用**目標**挑方向。砍特徵
不是「同一個模型跑更快」，是「換一個更小的假設空間」——那是建模決策，該由「這個
特徵對排序有沒有幫助」來決定。規則 1 講的就是這件事，而它已經寫在本報告 §2 裡，
我自己沒照做。

**分類的正確切法**：

| 類別 | 是什麼 | 誰決定 |
|---|---|---|
| A 同一個模型、跑更快 | 純工程 | 量完就能給 |
| B 換一個模型、跑更快 | 建模決策 | 使用者，量測只能提供數字 |

### 7.5 「`tune_hyperparameters` 裡有重複的工可以刪」→ 量了，沒有

拆到 step 層級後：`train` 佔該 node 的 96.6–98.8%，`predict`＋`score`＋
`prepare_datasets` 加起來不到 2%（§4.3）。

唯一真的重複的是 `prepare_datasets` ——每個 trial 都重新 `load().construct()` 一次
`lgb.Dataset`，20 次。但它生產外推只有 25 秒，佔 0.29%。

**`tune_hyperparameters` 已經是接近最精簡的形狀。** 外面沒有東西可以改了，能動的
只剩 `lgb.train` 內部（§5）。

### 7.6 「`force_col_wise: true` 省 12–20%」→ 量法造成的假象

第一次量出 col_wise 比 auto 快 17%，三輪配對一致，模型指紋相同——看起來是唯一一條
「同一個模型、跑更快」的路。

**第二次用不同量法得到 −5%，第三次得到 ±3.5% 且正負號在跳。** 差別在 `Dataset` 的
`construct()` 落在計時器的哪一邊：`force_col_wise` 是**建構期**參數，省的是 LightGBM
開跑前那次「該用 col-wise 還是 row-wise」的自動偵測測試，屬於一次性成本。第一次的
量法把建構放進計時器，第二三次放在外面。

**結論**：`auto` 本來就選了 col-wise，明著設沒有可拿的。**但 `force_row_wise` 一致
慢 12–25%——那不是機會，是地雷。**

**這條也暴露了一個壞掉的量尺**（規則 3）：第二次用 `booster.model_to_string()` 當
模型指紋，報告「3 種指紋、模型不一致」。查下去只有一行不同——`[force_col_wise: 0]`
vs `[force_col_wise: 1]`，那是參數字串，不是模型。**改用預測值的指紋，三個變體
逐位元相同。** 下結論前先驗指紋算法本身。

### 7.7 「換一台大機器能省 65%」→ 平行效率在 4 核之後就崩了

看到「4 核跑好幾小時、HPO 期間 Spark 被釋放、叢集閒置」，很自然推出「加核心」。
量之前我甚至報了「4 核 → 16 核約 3 倍，2.4 小時 → 45 分鐘」。

**實測：8 核只比 4 核快 15%，平行效率從 68% 掉到 39%**（§5.2）。Amdahl 天花板
4.5–6.3×，4 核 → 16 核只有 1.35–1.75×。**加核心仍是本輪最大的一條，但量級是
1.4–1.8 倍，不是 3 倍。**

教訓同 §7.1：「這個資源看起來不夠」不等於「補上去就會等比變快」。加核心之前先量
擴展曲線——那是半小時的事。

## 8. 量測本身撞到的坑

### 8.1 `--reset` 清不掉 training 的快取，量到的是「讀快取」

第一次量「16 倍列數」得到 60.9s，基準是 63.5s——**放大 16 倍反而略快**。這正是
「改了但輸出完全沒變 → 第一懷疑是改錯邊」的形狀（`00-core.md` §4 末）。

追下去：那一輪的 log 裡**完全沒有 `prepare.ds_train` 事件**，`feature_statistics.sample`
的列數跟基準一模一樣（73,337）。training 直接命中了上一輪的 `.bin` 快取。

根因：**dataset 版本雜湊是從 config 算的，不含資料內容**。只改客戶數 → config 沒變 →
版本沒變 → 快取路徑相同 → 命中。（改欄數會改版本，所以欄數掃描不受影響——但腳本
一律清，不靠這個巧合。）`scripts/local_spark_setup.py --reset` 只清 Hive warehouse，
清不到 `data/recsys_cache` 與 `data/dataset`。

**修法**：每輪清掉 `data/{recsys_cache,dataset,models,_scratch}`，並在腳本與
`analyze_train.py` 兩處加自檢——沒有 `prepare.ds_train` 事件的輪次直接排除。
量尺自己要看得出自己壞掉（規則 3）。

### 8.2 另一個 session 的 job 在同一台機器上跑，把讀數整個推走

同一組態（1,000 客戶 × 24 欄）跑三次：

```
08:33  training = 61.7s   每輪 2.10ms
09:02  training = 93.6s   每輪 2.68ms
09:04  training = 107.7s  每輪 4.07ms
```

**同樣的設定，最慢比最快慢 74%，而且是單調變慢**——那是漂移，不是雜訊。
先查熱降頻（`pmset -g therm`：無紀錄），再看負載：

```
load average: 13.46 (1分) / 9.95 (5分) / 8.04 (15分)   ← 8 核機器
```

`ps` 找到兩個 Spark JVM：一個是本輪的 `.worktrees/perf-training`，另一個是
**`.worktrees/split-rowwise`**——那個 worktree 在本 session 開始時還不存在
（開場的 `git worktree list` 沒有它），是另一個 session 中途開的。

**規則**：量效能之前先看 `uptime` 與 `ps`，確認機器上沒有別人的 job。這台機器同時
跑著多個 worktree 的 session，「我一個人在用」是預設錯誤的假設。事後才發現的話，
分得清楚哪些結論還站得住：

| 還站得住 | 站不住 |
|---|---|
| 跨 15–29 倍範圍的斜率與排序（10% 漂移撼動不了） | 任何精度宣稱與小數點 |
| 「誰是瓶頸」「管線佔比不到 2%」 | 10–30% 量級的效果（如 `force_col_wise`） |

**判斷方法**：這個結論所依賴的差距，有沒有大過雜訊？大很多就留著，同一量級就丟掉。

### 8.3 在背景執行中的 shell 腳本上做編輯，會把它改爆

量測跑到一半時去修 `run_train_profile.sh`，正在執行的那個 bash 直接爆
`unexpected EOF while looking for matching '"'`。bash 是**邊讀邊執行**的，改動會落進
還沒讀到的位置。

**規則**：背景跑的腳本，跑完再改。要改就先停。

## 9. 這份報告不能回答什麼

**外推是可以的，但要知道自己在外推多遠。** 本輪所有「生產會是 X 小時」的數字都是
外推，不是實測。以下是它們的極限。

### 9.1 最大的量測點是生產的 1/62

| 量測點 | 列 | 欄 | 格數 | 距生產 |
|---|---|---|---|---|
| `rows1x-cols24` | 73,337 | 23 | 1.7M | 1786× |
| `rows4x-cols24` | 291,030 | 23 | 6.7M | 450× |
| `rows16x-cols24` | 1,158,730 | 23 | 26.7M | 113× |
| `cols128` | 73,337 | 127 | 9.3M | 323× |
| `cols665` | 73,337 | 663 | 48.6M | **62×** |
| 生產 | 4,542,746 | 663 | 3.01B | 1× |

**本機到不了生產規模**：生產在 `to_numpy` 那一刻需要約 55 GiB（2026-07 OOM 調查 §3），
等比縮到 16,000 客戶 × 665 欄仍需約 14 GiB，量測機只有 16 GB。能逼近的極限約在
距生產 8× 處。

### 9.2 設計是 L 形的，缺的正是生產所在的那一角

量了「大列 × 小欄」與「小列 × 大欄」，**沒有量「大列 × 大欄」**。兩個效應相乘的假設
在 §4.9 登記了預測、§4.10 有驗證結果——但驗證點本身也只到距生產 15.6× 處。

### 9.3 沒有生產環境的 log

生產拿不到 `.jsonl`。唯一的生產側錨點是 2026-07 OOM 那次的兩行
（`read_parquet 69.52s`、`slice_features 14.09s` @ 4,542,746 × 665），來自事故現場、
不是受控量測。所有節點的生產耗時都沒有被直接觀測過。

### 9.4 什麼能搬、什麼不能搬

沿用 dataset 那輪的分界（規則 8）：

**能搬**：斜率的形狀（「只有 `tune_hyperparameters` 隨資料放大」）、node 之間的相對
結構（「管線不到 2%」）、被否決的假設。
**不能搬**：任何秒數與百分比。本機是 8 核壓成 4 核、16 GB、`local[*]` 單一 JVM；
生產是 4 核、128 GB、多 executor 叢集。

特別點名一個會誤導人的比例：本機基準規模下 `compute_test_mAP_spark`（20.5s）比
`tune_hyperparameters`（16.9s）**還大**。照本機佔比排優先順序會排錯——它的斜率是
0.23，外推到生產只值 59 秒。**本機的佔比不能拿來排生產的優先順序，只有斜率可以。**

## 10. 待拍板的決定（下一個 session 的起點）

### D1 — 要不要去要更大的機器？

**這是本輪唯一量級明顯的一條**，而且不改任何一行 code、不碰模型。但實測的天花板比
直覺低很多（§5.2）：4 核 → 16 核只有 1.35–1.75×。

**要之前先做一件半小時的事**：在生產機上跑一次 4 核 vs 8 核的對照，解出生產的實際
`p`。本機量到的 p=0.78–0.84 是在 29 萬列上測的；生產是 454 萬列，每輪工作量多 15 倍，
p 很可能更高——但那是推測，不是量測。**拿真實的 p 去要資源，比拿我的外推去要好講。**

### D2 — `max_bin` 255 → 63 要不要試？

−12.5%，是不歸 HPO 管的旋鈕裡最大的一條。但**會改模型**，需要一次準確度對照
（同樣的 HPO 設定跑兩輪，比 `macro_per_item_map`）。

**注意它與 D1 的耦合**：`max_bin` 降低會減少每輪的直方圖工作量，那也會改變平行
效率的曲線。兩件事一起做的話，效果不是相加。

### D3 — `compute_metrics_uncalibrated` 要不要跳過？

省 0.24%，修法乾淨（`method == "sigmoid"` 時沿用第一遍的值），風險低但不是零
（sigmoid 飽和的殘留情況，§6.1）。

**這條的價值不在省時間，在把一個「算了兩遍、必然相同、只用一個數字」的地方講清楚。**
要不要為 21 秒動一個正在運作的節點，是判斷題。

### D4 — 需不需要繼續往下量？

本輪最大的量測限制是**距生產 62×**（§9.1）與**機器上有別的 session**（§8.2）。
兩者都能改善，但都改善不了結論——98% 在 `lgb.train`、裡面的大旋鈕歸 HPO，這兩件事
在任何雜訊水準下都成立。

**建議停在這裡。** 再量下去只會把小數點磨得更細，不會換出新的方向。真正能推進的
下一步是 D1 的生產側對照，那不在這台機器上。
