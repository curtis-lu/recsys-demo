# 特徵表照接的鍵分兩類：entity 層級以 base key 接，候選層級以 identity 接、抽樣後才讀

ADR-0022 決定 1 說「特徵表可以多張，每張宣告自己的 join 欄位」。實作 #380 時的設計討論推翻了這一條的形狀，理由在效能：**兩類表的大小差很多，本來就該走不同的路，而「每張自己列 join 欄」讓框架分不出一張表該走哪條路。** 本 ADR 取代 ADR-0022 決定 1；ADR-0022 決定 2、3、4 沿用。

## 背景：兩類表，差一個數量級

```
entity 層級（今天就有）
feature_table ─fit、編碼一次、存 Hive、按月增量─▶ preprocessed_feature_table ─┐
                                                                             ├─ 以 base key 接
keys（抽樣後）＋ label ──────────────────────────────────────────────────────┤
                                                                             │
候選層級（本 ADR）                                                            │
candidate_feature_table ─只讀這次要讀的月份、編碼，不另存──── 以 identity 接─┴─▶ model_input
```

- **entity 層級的表**每個 entity 每期一列（示例的 `feature_table`），四個 split 共用，所以先編碼、存好、按月增量划算（ADR-0002）。
- **候選層級的表**一列是一筆候選，例如一次曝光的「曝光前 30 分鐘瀏覽幾次」。它跟 `sample_pool` 一樣大，而且**沒有抽樣**；keys 是抽樣後的子集。join 的成本主要花在讀這張大表。

如果每張表都自己列 join 欄，框架只能讓所有表走同一條路（其中一類必然吃虧），不然就要使用者再多指定一個「走哪條路」。

## 決定

1. **特徵表照 join 的鍵分兩類，名字照鍵取，不照新鮮度取**（`CONTEXT.md` 的 **entity 層級特徵表**、**候選層級特徵表**）。
   - entity 層級：以 base key（`time` ＋ `entity`）接，**恰好一張**，就是 `feature_table`。路徑與今天完全相同。
   - 候選層級：以 identity 接，**選用、最多一張**。宣告方式是在 catalog 加一個固定名字的條目 `candidate_feature_table`，指到部署自己的實體表；跟 `feature_table`／`sample_pool`／`label_table` 同一個模式。
   - 其他形狀框架不收，在來源 SQL 展開成兩類之一：比 base key 粗的表（例如只有 `time` ＋ 使用者）展開到每個 entity；只以 item 接的表展開到每一列候選。
2. **候選層級表在組 model_input 時才讀、才編碼、才接，不另存。** 在抽樣前另存一份，等於把之後會被抽掉的大量負例也多寫一遍——ADR-0022 否決「一次曝光一列的寬表」用的是同一個理由。只讀這次要讀的月份：一般執行是 train ＋ val ＋ 還沒落地的 test 月，`--only-test-months` 只有還沒落地的 test 月（`month_plans.py::candidate_feature_table_months`）。identity 含 `time`，所以這個篩選只影響成本、不影響答案。類別欄用 fit 出來的詞表編碼，沒見過的值變成未知值代碼，與 entity 層級相同。
3. **找不到的列補 NULL，列留著**，與 entity 層級相同（ADR-0005）：丟列會悄悄改掉候選集合，mAP 的母體跟著變。**整個月都沒有資料則報錯**：一張每次都整段重讀的表少了一個月，會變成一整個月的 NULL 特徵而沒有人發現。
4. **檢查**：
   - B5／B6／B7 兩張表都查（B5、B7 的錯誤訊息點名是哪張表）；B12（特徵欄不得與無正例組的權重欄同名，ADR-0025 決定 3）也看兩張表的特徵。候選層級表的 identity 欄是 join 鍵，不當特徵，也不從它讀詞表（item 的完整值域在 `schema.categorical_values`，這張表只有被展示過的那些）。
   - 新增 B13（候選層級表缺 identity 欄）與 B14（同一個特徵欄兩張表都有）。只看欄名，不掃資料。
   - **B8 在候選層級表上改成掃一次這次要讀的月份**，算每個整數欄與 decimal 欄的絕對值最大值；同一次掃描順便回答「哪些月份有資料」。這張表不落地，沒有框架自己寫的檔尾統計可讀；框架也不規定使用者的表是什麼格式。這是 ADR-0006「檢查不做整表聚合」的例外，在該 ADR 補記。類別欄不在掃描內：它們在轉型之前就被編碼成詞表索引，原始值不是被轉型的那個值。
5. **宣告了候選層級表，離線推論在 CLI 入口擋下**（A47，ADR-0022 決定 4 的新形狀）。推論 pipeline 只讀 `feature_table`，而這種設定下訓練的模型需要候選層級表的欄：放行的話它不會悄悄算錯，而是在啟動 Spark、讀完評分母體之後，才以 `Missing feature columns` 失敗，訊息不說是哪張表、也不說出路。所以這道閘換到的是「提早、講清楚原因地停下」。讓推論也讀這張表不做（#380 的 Out of scope）：曝光資料的部署裡，推論的候選（entity × 全部 item）沒有一筆被展示過，這張表本來接不到；全網格部署的候選層級表（以 `time`、`entity`、`item` 為鍵）原則上接得到，先擋下讓之後要支援時不必打破任何設定。只宣告 `event`／`occasion`、沒宣告候選層級表時，推論照跑，與今天相同。
6. **版本號**：候選層級表的欄名與型別只在宣告時進 `base_dataset_version`（`candidate_feature_table_fingerprint`，自己的 payload 鍵）。沒宣告時 payload 與今天逐位元相同。

## 考慮過、沒選的做法

**每張表自己宣告 join 欄（ADR-0022 決定 1 原案、#380 票面）。** 什麼形狀都收，SQL 不用改。但設定要列欄、要檢查欄在不在、是不是 identity 的子集、會不會撞名；更重要的是它看不出一張表該走「先編碼存好」還是「抽樣後才接」。

**候選層級表也先編碼、存 Hive。** B8 可以照舊讀檔尾、可以撈出來看，但要在抽樣前把整張最大的表多寫一次。

**讓候選層級表宣告接在 occasion 層級（query group）。** 如果一個部署的即時特徵全部是「整次請求共用」的（例如請求前 30 分鐘瀏覽幾次），表會小 k 倍（k 是一次請求平均幾個候選，示例約 4），join 比較快。沒選：今天唯一的實例 `feature_realtime` 有跟 item 相關的欄，本來就得接在候選層級；而且之後要加是**純新增**——多一個選填鍵、預設 identity，沒寫的設定版本號不變。等真的有部署的即時特徵全部是請求層級再加。

**最多兩張：一張 occasion 層級、一張候選層級。** 兩種欄都有時（最常見的情況）要 join 兩次、搬兩次大表，比放在同一張候選層級表裡慢。

**B8 不擋候選層級表、只寫文件。** 整數在 1677 萬以內轉 float32 不會失真，計數類特徵通常很安全。沒選：`numeric_precision_policy` 預設是 `block`，這個框架的立場是「值被改掉要擋」；候選層級表不擋等於開一個洞。代價是多掃一次，在下面〈後果〉。

**廣告示例跑兩趟，保留「宣告 occasion 的離線推論」的實跑。** 示例宣告了候選層級表之後推論被擋，這條路就沒有實跑了。沒選：推論的資料裡沒有 occasion 欄（`scored_row_columns` 會丟掉它），任何誤用含 occasion 的鍵都會直接報「找不到欄」，不會悄悄算錯；跑兩趟換到的只是提早發現一個會報錯的問題，代價是 e2e 多約 1 分鐘、腳本要在兩趟之間切換設定。

## 後果

- **候選層級表每次執行被讀好幾次。** 四個 build 都把它篩到「這次要讀的全部月份」（train ＋ val ＋ 還沒落地的 test 月），不是各自 split 的月份：keys 是落地表，Spark 不會照 keys 的月份再修剪。所以一般執行時四個 build 各讀一次全部月份，B8 再讀一次（多 25%），fit 另外讀 train 月份兩次（月份檢查與詞表）。若改成各 build 只讀自己 split 的月份，build 端的讀取量約減半，B8 相對變成多 50% 以上。`numeric_precision_policy: truncate` 只讓超標的值通過，不省這次掃描。
- **候選層級表的類別欄出現 train 沒見過的值時，不會有 warning。** entity 層級在 `apply_preprocessor_to_features` 數一次未知值；候選層級在每個 split 組 model_input 時才編碼，數它要多一次 Spark 動作。值照樣編成未知值代碼。
- **重複的 identity 列只有 train／train_dev 抓得到**（B10 的既有範圍）。val／test 月份才有的重複會讓列數悄悄變多。上游的 `max_duplicate_key_ratio` 是真正擋它的地方。
- **廣告示例不再實跑離線推論。** 示例 README 寫明。ADR-0025〈後果〉把「形狀二的示例實跑（含離線推論）」當作驗得到 occasion 歸類的地方；那一段實跑從此不再發生，理由見〈考慮過、沒選的做法〉最後一段。
- **全網格部署也會失去離線推論。** 宣告了候選層級表就擋，不看它是不是曝光資料：一個全網格部署若把逐 (entity, item) 的特徵（例如「這個客戶這期有沒有持有過這個產品」）或隨時間變的 item 屬性放進候選層級表，離線推論一樣被擋。這類特徵要留在離線推論可用的部署裡，今天的做法是在 `feature_table` 的 SQL 裡把它按 item 攤成多欄（每個 item 一欄），item 多時欄會很多。這是 #380 的 Out of scope 帶來的限制，不是設計上必要的。
- **A47 看的是 catalog，不是模型。** 加上條目之前訓練的舊模型也會被擋。
- **回補候選層級表會讓一個版本裡混兩個時期的值。** train／val 每次執行都重讀這張表；test 的 model_input 是增量的，已落地的 test 月份不會重讀。候選層級表回補、或換成同 schema 的另一張表時，`base_dataset_version` 不變，重跑 dataset 的結果是 train／val 用新值、已落地的 test 月份還是舊值，沒有檢查會紅。回補之後要對已落地的 test 月份下 `--rebuild-dates`。`feature_table` 沒有這個問題：它整個是增量的，回補後不下 `--rebuild-dates` 就是每一段都用舊值，至少一致。
- **identity 值對不上時，候選層級特徵會悄悄全變成 NULL。** 例如兩邊的時間戳精度或時區不同。月份檢查（只看月份在不在）與 B10（只看列數）都擋不到。這與 `feature_table` 的覆蓋率沒有閘門是同一個決定（ADR-0005）；差別是候選層級表的鍵多、比較容易對不上。
- ADR-0022 的已知風險沒有變：即時特徵在線上與離線是兩份算法，算得不一樣時模型會悄悄變差。
- 「怎麼被擺出來」的特徵（位置、這次請求裡第幾次出現）只寫文件，不做「訓練用真實值、評分固定成常數」的機制（#380 留言 §4；使用者 2026-09-22 裁決）。

## 更正 ADR-0022

- **決定 1 由本 ADR 取代**：不是「多張、每張宣告自己的 join 欄位」，而是兩類、鍵由類別決定、各最多一張（entity 層級恰好一張）。
- **決定 4 的觸發條件**改成「宣告了候選層級特徵表」。
- 決定 2（往回算在使用者 SQL 做）、決定 3（框架不檢查偷看）沿用。但 ADR-0022 否決「一次曝光一列的寬表」的第二個理由（前處理在抽樣之前做，連要丟的負例也處理）對候選層級表不成立——它在抽樣後才讀。所以要「每一次曝光用它當下拿得到的那份快照」時，把快照欄算進候選層級表就是做法，代價只剩列寬。
- 〈後果〉列的「dataset 收多張特徵表要動的地方」大半仍然成立，但「前處理的 apply」與「feature_table fingerprint」的改法不同：apply 完全不動，候選層級表的 fingerprint 是另一個 payload 鍵。`core/consistency.py` 的 `DATASET_SOURCE_TABLES`（A32：這幾張表的 ETL 設定必須留著重複鍵檢查）沒有加入候選層級表。A32 只看 parameters，拿這份清單裡的名字去 ETL 設定找表；`candidate_feature_table` 是 catalog 的邏輯名，實體表叫什麼由部署決定（示例是 `feature_realtime`），用這個名字在 ETL 設定裡找不到東西，A32 對找不到的表是跳過。**所以沒有東西守候選層級表的重複鍵設定**：它 ETL 設定裡的 `max_duplicate_key_ratio` 被刪掉時不會有人報錯，之後的重複列只剩 B10（train／train_dev）抓得到。要補的話，A32 得改成讀 catalog 解析出實體表名，不在本 ADR 範圍。
