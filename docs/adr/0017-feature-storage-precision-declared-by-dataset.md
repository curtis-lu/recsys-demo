# 數值特徵的儲存精度由 dataset 宣告，整數靠 2^24 擋

> **實作狀態（2026-09-03）**：決策已定，實作在 #281（宣告與閘門）與 #283（把收斂做完）。
> 本檔寫的是決策當時的推導；實作落地後若有偏離，以程式碼為準並回頭修這裡。

`build_model_input` 的註解早就寫著「**numeric features converge on one storage type**」，
但實作只做了一半——`preprocessing` 的 cast helper 只轉 `DecimalType` 與 `DoubleType`，
整數族與 boolean 逃掉了。後果是 pandas 把 float32 與 int64 混在一起取 `.values` 時共同型別
升成 float64，**一個整數特徵欄就讓整個模型輸入矩陣翻倍**；float32 混 boolean 更慘，會變成
object dtype。

把那個決定做完的時候有三個問題要回答：**精度由誰宣告、在哪一層宣告、以及轉不過去的欄怎麼辦**。
這條 ADR 回答它們。

## 決定

1. **目標儲存型別由 dataset 設定宣告**，合法值 `float32` / `float64`，預設 `float32`。
   它改變 parquet 內容，所以進 `base_dataset_version`。
2. **training 階段不提供任何精度選項。** `extract` 從 parquet 的實際型別決定矩陣 dtype，
   並與宣告值交叉檢查，不一致就報錯。
3. **cast 涵蓋所有數值特徵欄**——Decimal、Double、Float、整數族、boolean。identity 欄與
   label 欄維持不轉。
4. **轉不過去的判準是 `max(|x|) > 2^24`**（目標為 float32 時），對 int 與 float 是同一條規則。
5. **閘門觸發時的行為由另一個鍵決定**（擋下來，預設；或放行截斷），而那個鍵**不進版本雜湊**。

## 為什麼宣告在 dataset 階段，不在 training 階段

精度是**儲存的資料**的性質，不是消費端的偏好。

若 parquet 存的是 float32，在 training 端要一個 float64 的矩陣，只會多吃一倍記憶體換到
**零資訊**——float32 加寬成 float64 是補零，不會讓任何數字變準。所以「training 端的精度選項」
是一個只能把事情變糟的旋鈕。

反過來說，真的要 float64 就得讓 parquet 真的存 float64，而那必然是 dataset 階段的事，
必然翻版本、必然重算。**那個成本是真實的，不該被藏在一個看起來很輕的 training 旗標後面。**

推論：精度只有一個宣告點。多一個就多一條漂移路徑——「train 用一種精度、val 用另一種」是
這條 ADR 明確要防止的狀態。

## 為什麼判準是 2^24，而且 int 與 float 共用它

float32 的尾數是 24 bit。所以它在每個量級能分辨的最小差距（ulp）是固定比例的：

```
量級 1              → 1.19e-07
量級 1,000,000      → 0.0625
量級 16,777,216     → 2          ← 2^24，這裡開始連相鄰整數都分不出來
量級 1,000,000,000  → 64
```

統一的判準是「**該欄相異值的最小間距 >= ulp(該欄的最大絕對值)**」。整數欄的最小間距恆為 1，
代入之後就化簡成 `max(|x|) < 2^24`——所以那條看起來只適用於整數的規則，其實是統一判準的
整數特例，不是另一條規則。

這個判準對整數是**精確**的，不是啟發式。實測：

```
max 恰為 2^24        20 萬個相異整數 → float32 後仍是 20 萬個，零損失
max 為 2^24 + 1,000  20 萬個相異整數 → float32 後剩 199,501，開始 collision
```

`collision` 才是分水嶺：兩個不同的輸入被映射成同一個值，正是會改變排名的東西。

boolean 恆為 0/1，永遠安全，不需要檢查。

### 為什麼不用「有沒有 collision」當閘門

因為**幾乎每一欄都會有**。實測（各 100 萬列）：

| 欄 | 相異值 f64 → f32 | 有 collision | 實際有害 |
|---|---|---|---|
| 比例 0~1 | 1,000,000 → 980,520 | 是 | **否** |
| 金額（元）0~10 億 | 999,476 → 979,630 | 是 | **否** |
| 日期寫成數字 20250101 | 1,130 → 566 | 是 | 是 |
| 帳號 ID（1e10 級） | 632,303 → 978 | 是 | 是 |
| 極細 float（1e-9 差） | 1,000 → 9 | 是 | 是 |

二元的 collision 判準會對第一、二列誤報。而要分辨「塌了但無害」與「塌了且有害」需要**欄位語意**
——機制本身給不出門檻。所以閘門只擋整數那條可證明的線，其餘交給使用者（見下一節的旋鈕）。

## 為什麼閘門政策的鍵不進版本雜湊

因為它**不改變成功時產出的資料**：同一份設定跑成功，parquet 內容一模一樣，差別只在「踩到時
要不要停」。把它放進雜湊會導致「只改閘門政策就要整批重算」——那是純粹的浪費，而且會讓人
為了省重算而不敢調整閘門。

比照 `COVERAGE_ONLY_KEYS`（ADR-0001）的既有機制排除。

## 為什麼預設是 `raise` 而不是截斷

因為靜默截斷的失敗模式是**分數變了但沒人知道**。生產環境的分數不會逐次被人檢視，一個
warning 在幾百行 log 裡等於不存在。

而選 `raise` 的代價很低：使用者只要看一眼被指名的欄位與它的最大值，就能判斷「這欄的高位數
有沒有意義」。累計筆數這種欄截掉尾數多半無害（LightGBM 反正只分 256 個箱），但那是**使用者
才知道的事**——所以給旋鈕，但要他明寫。

## 考慮過但否決的選項

| 方案 | 為什麼否決 |
|---|---|
| dtype 選項放在 training 設定 | parquet 已是 float32 時要 float64 是純浪費；且製造第二個宣告點 |
| 用 `approx_count_distinct` 偵測 collision 當閘門 | 對幾乎每一欄誤報（見上表）；成本是千萬列 × 兩千個 HLL sketch |
| 用「分箱邊界有沒有變」當閘門 | 實測分不開安全與有害的欄——float32 的相對誤差固定在 1e-7 量級，每一欄的分位數邊界都會動一點點 |
| 用 `max_bin × 4` 當門檻 | 那個係數是為了讓答案符合預期而挑的，沒有依據 |
| 只在 numpy 端轉型、不動 Spark 端 | 會留下「parquet 說一套、記憶體裡是另一套」的落差，正是這次 bug 的形狀；boolean → object 的地雷也還在 |

## 代價

- **翻 `base_dataset_version`**：preprocessor／val／test 重算，train 系列連坐。這是本次計畫
  最大的時間成本。
- **既有 Double / Decimal 欄轉 float32 有沒有壓扁它們，這條 ADR 不回答。** 那個轉換現在就在
  跑、已上生產好幾個版本，是既存行為而不是本次引入的風險。要查是獨立的事，而且應該針對
  懷疑的少數欄單獨量，不必為它付全表的量測成本。
- **整數欄超過 2^24 的使用者會被擋下來**，必須做一個決定（改欄位表示、或改用 float64、或明寫
  放行）。這是刻意的：那個決定本來就該有人做。

## 這條 ADR 沒有解決的事

- **閘門怎麼取得 `max(|x|)`，尚未定案。** ADR-0006 明訂「dataset 閘門維持零掃描」，理由是
  「加一條全掃會改變這個節點的成本量級，而公司規模下的成本未知」。一次 Spark 聚合會違反那條。
  已驗證的替代路徑是**讀 parquet footer 的 per-column 統計值**：實測值與實掃完全相符，且快 32 倍
  （200 萬列時 11.9ms vs 374ms），倍數隨資料量放大。**待決**：footer 沒有統計值時要退回掃描
  還是 raise。決定之後回頭補這一節。
- **效能修法不寫進 ADR。** 本次一併處理的三個效能問題（group id、樣本權重、Spark cast 的計畫
  爆炸）雖然「沒有脈絡會讓人困惑」，但它們既不難反轉、也沒有取捨——嚴格更好。把沒有取捨的
  東西寫進 ADR 會稀釋 ADR。它們的家是 `docs/operations/known-pitfalls.md` 與就地註解。
