training pipeline 流程圖

node 層級的 DAG：誰產出什麼、誰吃什麼。對照 src/recsys_tfb/pipelines/training/pipeline.py::create_pipeline。 姊妹圖 dataset-pipeline.html、 inference-pipeline.html； 跨 pipeline 的完整 lineage 見 data-lineage.html。

框內是 node name，可以直接餵給 --from-node / --only-node（--list-nodes 印的也是這個名字）。 這條 pipeline 的 node name 都與函式名相同，函式全部在 pipelines/training/nodes.py（#489 之前有 7 個診斷 node 的函式在 diagnosis/model/ 底下，ADR-0030 決定 6 把它們搬回來，機制進 steps/）。
刻意不畫：每個 node 都吃的 parameters、 compute_group_filter_report（pipeline 實際有 20 個 node，本圖畫了 19 個； 這是既有落差，與 calibration 移除無關，未在本輪一併補上）、 --rebuild-dates 與 --fresh-hpo（只推翻「跳過」的決定，跳過的與重算的走同一條線）、 HPO 的 journal／checkpoint 檔案（node 內部的續跑機制，不是 catalog 條目）、以及 finalize_model 的兩個策略（吃同一組宣告輸入）。

圖例

來源表（這裡全部是 dataset pipeline 落地的 Hive table） 上游 pipeline 落地的版本化 artifact（檔案，不是表） node（框內為 node name） side-effect sink：outputs=None，產物寫到 catalog 以外的地方
落地的 catalog 條目（Hive table／JSON 檔） MemoryDataset：catalog 沒這個名字，只活在這次 run 的記憶體 別的 pipeline 會吃的產物

沒有六角形。dataset 有 Layer-2 資料閘、inference 有發布閘，training 一個都沒有——檢查全部在 CLI entry 跑完（Layer-1 的 validate_config_consistency、A21 的 --rebuild-dates ⊆ dataset.test_snap_dates），在 Spark 冷啟動之前，不是 node。
接點記號有兩個方向。VPMT 標在產物上，node 框裡的「＋ P · M」代表它同時吃這幾個； L反過來，標在產物上代表「log_experiment 吃它」——它一個人吃十個輸入， 十條線畫出來會蓋掉整張圖。V=preprocessor_view（5 個消費者）、 P=preprocessor（6 個）、M=model（8 個）、 T=train_parquet_handle（4 個）。 V 與 P 是兩份不同的東西，不是同一份的兩個名字——見下方第 4 點。
粗虛線邊 = node 自己寫的表（Node(writes=…)），而且它不是拓樸相依邊； 細虛線邊是宣告了但函式根本沒讀的參數（畫出來的只有一條，見第 3 點；另一條是 gain_ledger → log_experiment，藏在 L 記號裡沒畫）。
SVG 與 .mmd 同步於 2026-09-01（程式碼基準 8fdd333，逐條回原始碼查證； 上一次是 2026-08-19 的 4de7299）。 .mmd 永遠是唯一真實來源；這頁內嵌的 SVG 是它的渲染結果，渲染步驟見頁末。 改了程式碼卻只改 .mmd 沒重渲染，這頁就會開始說謊。

流程圖

來源：docs/diagrams/training-pipeline.mmd。node 順序以 pipeline.py 的插入順序為準。

四件只讀 pipeline.py 看不出來的事

1. Spark 在中間被刻意關掉，而快取節點根本沒讀它的輸入資料

四個 cache_* node 的宣告輸入是 dataset 落地的 Hive 表，runner 會把它 load() 成 Spark DataFrame 餵進去——然後沒有一個 node 讀它的資料。 node body 只拿 df.sql_ctx.sparkSession 取得 session，資料走 Hadoop FileSystem.copyToLocalFile 從 Hive table location 直接搬到 driver-local parquet（steps/local_cache.py::populate_cache_from_hive → utils/hdfs.py::copy_hdfs_to_local：經 spark._jvm 的 JVM bridge，不依賴 PATH 上的 hadoop CLI，也不起 Spark job）。 型別守衛是 steps/local_cache.py::require_spark_input；「什麼算 cache hit」這個決策 刻意留在四個 cache_*_model_input 的 node body 裡（ADR-0014 決定 1 拆掉了舊的 _materialize_parquet_handle，那個名字現在 src/ 裡已經不存在）。 df 不是 Spark DataFrame 時 raise TypeError—— 它是 session 的把手，不是資料的入口。

跨出 Spark 之後，tune_hyperparameters 的函式體第一行就呼叫 release_spark_session()（utils/spark.py）：HPO 到 finalize 可能跑數小時，閒置的 application 會被叢集回收、context 在 JVM 端死掉，之後寫 Hive 就撞 IllegalStateException。 放第一行而不是新增一個 DAG 節點，理由寫在那段註解裡——Runner 循序執行，「函式第一行」在構造上等於 「前面的節點都跑完了」；零入度節點的排序取決於宣告位置，靠不住。 session 由第一個再碰 Hive 的呼叫自動重建（HiveTableDataset 走無參數的 get_or_create_spark_session() → utils/spark.py::_rebuild_or_active）， 實際上就是 predict 節點查「哪些分區已經寫過」的那一刻。

所以圖上三個 subgraph 的分界不是美觀分組，是 Spark 活著／死著的分界。 本圖畫了 19 個 node，其中只有 7 個會碰到 Spark：四個 cache_*、 predict_and_write_test_predictions、compute_test_metrics、select_shap_population。 （pipeline 實際有 20 個 node：沒畫出來的 compute_group_filter_report 不碰 Spark， 所以 Spark 的計數不受影響；這個落差是既有的，與 calibration 移除無關，也未在本輪一併補上。）

2.「只讀 test 月份」與「只讀計分月份」：同一張表，兩個消費者各自決定

training_eval_predictions 的 catalog 條目 partition_filter 只鎖 model_version，月份沒有任何東西擋，表裡是這個 model_version 累積過的所有 test 月份。 兩個消費者各自裁。select_shap_population 只讀 dataset.test_snap_dates——這次預測、 compute_shap_diagnostics 描述的月份——test_model_input 也照同樣的月份裁（ADR-0030 決定 12；以前照單全收，成本跟著表的歷史長）。 compute_test_metrics 裁到計分月份 （test_metrics.snap_date，沒寫＝dataset.test_snap_dates；ADR-0028）：它的分數是 promote 挑版本的依據， 跟著表裡累積了哪些月份變，兩個版本就可能考不同的考卷；表裡其他月份它不讀，log 列出略過了哪些（從檔案清單讀，不跑 Spark job）。 兩邊用同一個比法：當文字比（steps/scored_months.py::restrict_to_scored_months）。

代價由 steps/predict_months.py::warn_about_surplus_partitions 說出來：item 改名會留下 surplus 分區，重跑刪不掉， 會一直混進計分月份的 metric，所以那裡發 warning 而不是靜靜跳過。 看到同一個標記不要假設同一個結論——「跨月累積」是共同的事實，「要不要裁」是各自的決定（inference 圖上的兩個消費者也各自裁）。

3. 增量在這條 pipeline 出現三次，三種機制，一個共同的出口

  • parquet 快取（四個 cache_*）：命中與否只看 _SUCCESS 在不在，不看新舊。 test 是一個月一個目錄一個 _SUCCESS，所以加一個月只複製那個月。
  • 預測（predict_and_write_test_predictions）：一個 (model_version, snap_date) 的預測是不可變產品——model_version 雜湊了所有定義模型的東西， 同模型同月份預測逐位元相同，重算沒有收益。「完整」的定義是「這個月已寫的 item 分區恰好等於快取裡的 item 集合」， 不是「有分區就算數」（steps/predict_months.py::months_already_written）：弱的那個判準會把跑到一半死掉的 run 當成完成，讓缺的 item 永遠缺下去。
  • HPO（tune_hyperparameters）：Optuna study 以 search_id 為鍵持久化在 data/models/_hpo/<search_id>/，崩潰後只補剩下的 trial，調高 n_trials 是延長同一場搜尋而不是重開一場。

三者共同的代價是 --rebuild-dates / --fresh-hpo：上游回填會改變輸入而 不改變任何版本號，所以必須有一個「明說要重來」的出口。 ADR-0012 把產物層的 skip-if-exists 標為「預設值站錯邊」的那一種，並否決把它擴到 dataset 全部產物。上面三項裡 只有第 1 項（parquet 快取）真的落在那個靶心——predict 以 model_version、 HPO 以 search_id 為鍵，兩者都是雜湊過的版本 ID，不是「版本號完全不參與」。 第 1 項是刻意付這筆帳。這也是為什麼快取的強制刷新會在 _SUCCESS 清不掉時 raise 而不是繼續（cache_test_model_input 的 --rebuild-dates 分支）—— 存活下來的 _SUCCESS 會被讀成命中，於是這個「重建」會安靜退化成它本來要防的那次陳舊重跑， 產出一模一樣的數字。

4. preprocessor 與 preprocessor_view 是兩份東西，訓練鏈與診斷各吃一份

P preprocessor 是 dataset pipeline 落地的 JSON； V preprocessor_view 是 select_features 對它套一次 training.feature_selection.exclude 之後的產物，memory-only、不在 catalog 裡。

  • 吃 V 的是訓練鏈：prepare_train_inputs、 compute_sample_weight_report、tune_hyperparameters、 finalize_model、predict_and_write_test_predictions （共 5 個）。
  • 吃 P 的是 select_features 自己，加上五個 diagnosis node： compute_feature_statistics、compute_gain_ledger、 compute_shap_diagnostics、compute_quadrant_profiles、 compute_quadrant_cases。

這個切分是刻意的，不是漏接線。診斷改吃落地的 P 之後，只跑診斷的接續執行不會再把 select_features 與整條訓練鏈 拉回來——那正是這次改動要買的東西。哪個節點才是「特徵欄有哪些」的權威？答案是模型自己： 診斷從 model.feature_names() 建 view，P 只提供其餘 metadata。

代價落在 compute_feature_statistics：它為了這件事同時也吃 model， 於是被推到 finalize_model 之後（見對照表那一列；#411 移除校準器前， model 的生產者是 calibrate_model）。

（皆 MemoryDataset）		 全圖唯一的虛線邊 predict_manifest 在函式裡從頭到尾沒被讀過 （函式裡只出現在簽名與 docstring）。掛它純粹是排序：三個資料輸入都沒有 node producer， Kahn 拓樸排序會把這個 node 浮到 predict 之前，讀到還沒寫入的預測。

兩個實測過的坑：(1) .mmd 裡不要留「只有 %%、後面沒有字」的空註解行—— mermaid 不會把它當註解剝掉，會黏成 %%flowchart 然後報 parse error 在第 1 行，很難聯想；要空行就用真正的空行。 (2) 用 mermaid-cli@10 不要用 @11：v11 的新 renderer 改用 rough.js 畫形狀， 同一張圖會從幾十 KB 灌到數百 KB。
版面上的一個取捨：preprocessor ／ select_features ／ preprocessor_view 刻意不包進 subgraph，而且 preprocessor_view 只往 prepare_train_inputs 拉一條真實邊、其餘 4 個消費者交給 V 記號。 橫貫線畫出來會把主鏈整個蓋掉；一條錨定邊足夠讓讀者知道它不是死節點。 preprocessor（6 個，其中 5 個是 diagnosis node）、model（8 個）與 train_parquet_handle（4 個）同理——分別交給 P M T。
