inference pipeline 流程圖

node 層級的 DAG：誰產出什麼、誰吃什麼。對照 src/recsys_tfb/pipelines/inference/pipeline.py::create_pipeline。 姊妹圖 dataset-pipeline.html； 跨 pipeline 的完整 lineage 見 data-lineage.html， 各 node 的設定與執行前檢查見 inference.md。

框內是 node name，可以直接餵給 --from-node / --only-node（--list-nodes 印的也是這個名字）。 這條 pipeline 的六個 node name 都與函式名相同。刻意不畫：每個 node 都吃的 parameters （唯一例外是 inference.products，理由見圖例）、use_calibration 的校準開關 （它只是 predict_scores 內部一次 if，不改變任何一條邊）、以及 build_scoring_dataset 只寫 log 不下推的特徵覆蓋率報表。

圖例

來源表（read_only） 被造成資料列的 config 值 上游 pipeline 落地的版本化 artifact node（框內為 node name） 閘：不轉換資料，只決定放不放行
落地的 catalog 條目（Hive table） MemoryDataset：catalog 沒這個名字，只活在這次 run 的記憶體 production 產物 失敗路徑的終點（沒有東西被寫出去）

只有一種 config 入圖。inference.products 不是「被讀取的設定值」，而是被 spark.createDataFrame 造成一張表、再 crossJoin 進評分母體的資料列 （nodes_spark.py:113-115）——評分列數 = entity 數 × 日期數 × products 數。 inference.snap_dates 這種純過濾條件仍然不畫。
虛線邊 = 不是資料流：宣告了但函式沒讀（scoring_dataset → predict_scores）， 或版本解析的相依（model ⇢ preprocessor）。

流程圖

來源：docs/diagrams/inference-pipeline.mmd。node 順序以 pipeline.py 的插入順序為準。

三件圖上看得到、只讀程式碼容易漏掉的事

1. node 之間不是傳 DataFrame，是走 Hive round-trip

runner 對每個 input 都呼叫 catalog.load()（core/runner.py:87）。 score_table 與 ranked_staging 是 Hive managed table，而且 catalog 條目沒有設 partition_filter（對照組：enriched_eval_predictions 有），所以讀回來的是 含歷史 partition 的全表——別的 model_version、別的日期都在裡面。 這就是 rank_predictions 與 validate_predictions 都先呼叫 _filter_current_inference_scope 的理由：把資料限縮回本次的 model_version × inference.snap_dates。圖上標「全表讀回」的那兩條邊就是這件事。

2. ranked_staging 存在的唯一理由是失敗路徑

驗證失敗時 validate_predictions 直接 raise ValidationError，整批中止： production 的 ranked_predictions 完全不被觸碰，失敗批次留在 staging 供事後排查。 publish_predictions 的函式體只有一行 return validated_predictions—— 真正的 production 寫入是 catalog 對這個 node 輸出做的 save。 把紅色那條路徑遮掉，staging → validate → publish 會被讀成三個沒必要的步驟。

3. 模型決定了配哪份前處理，而模型由人決定

inference 預設解析 data/models/best symlink（core/versioning.py:301）， 該 symlink 只能由使用者跑 scripts/promote_model.py 設定——這是整條 pipeline 唯一的人工介入點。 選中的模型再從自己的 manifest 回溯 base_dataset_version，決定要載 data/dataset/<base_dataset_version>/preprocessor.json。 所以 model 與 preprocessor 不是兩個獨立輸入；圖上那條點線就是這個相依。 manifest 缺欄時 CLI 會 warning 並 fallback 到 dataset 的 latest—— 那是舊產物相容機制，不是正式流程（見 inference.md §2）。

（MemoryDataset）		 參數名不符 函式第一個參數叫 ranked_predictions， 但 pipeline.py:41 餵進去的是 ranked_staging；圖與本表一律用 catalog 名。

（Hive，production）		 函式體是 identity；production 寫入是 catalog 對這個輸出做的 save。 走到這裡代表閘已通過，所以這是整條 pipeline 唯一一次 production 寫入。

實際執行序由 runner 依相依性決定（--list-nodes 可印出這次會跑哪些）。 三張 Hive 表都採 dynamic partition overwrite，partition 為 snap_date × prod_name × model_version。

圖的真實來源是 docs/diagrams/inference-pipeline.mmd（Mermaid，純文字）。 這頁內嵌的是它渲染出來的 SVG——改圖請改 .mmd，不要直接動這頁的 SVG，否則兩邊會分岔。

兩個實測過的坑：(1) .mmd 裡不要留「只有 %%、後面沒有字」的空註解行—— mermaid 不會把它當註解剝掉，會黏成 %%flowchart 然後報 parse error 在第 1 行，很難聯想；要空行就用真正的空行。 (2) 用 mermaid-cli@10 不要用 @11：v11 的新 renderer 改用 rough.js 畫形狀， 同一張圖會從幾十 KB 灌到數百 KB。
版面上的一個取捨：model 與 preprocessor 刻意不包進 subgraph。 包起來 dagre 會把整個 cluster 當一個整體擺到側邊，主鏈會被拉成右→左→中的鋸齒； 讓這兩個節點自由落在各自消費者的上方，主鏈才是一條可以一路讀下來的直線。

不想裝工具的話：把 .mmd 全文貼到 mermaid.live， 或貼進任何 .md 的 ```mermaid 區塊讓 GitHub 直接渲染。
