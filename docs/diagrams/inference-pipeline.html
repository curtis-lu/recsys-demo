inference pipeline 流程圖

node 層級的 DAG：誰產出什麼、誰吃什麼。對照 src/recsys_tfb/pipelines/inference/pipeline.py::create_pipeline。 姊妹圖 dataset-pipeline.html、training-pipeline.html； 跨 pipeline 的完整 lineage 見 data-lineage.html， 各 node 的設定與執行前檢查見 inference.md。

框內是 node name，可以直接餵給 --from-node / --only-node（--list-nodes 印的也是這個名字）。 這條 pipeline 的五個 node name 都與函式名相同。刻意不畫：每個 node 都吃的 parameters （例外是 inference.products 與 inference.entity_buckets，理由見圖例）、 use_calibration 的校準開關（它只是評分節點內部一次 if，不改變任何一條邊）、 續跑的 chunk 規劃（它決定跑幾個 chunk，但跳過的與寫出的走同一條線）、以及 build_inference_population_features 只寫 log 不下推的特徵覆蓋率報表。

圖例

來源表（read_only） 被造成資料列的 config 值 上游 pipeline 落地的版本化 artifact node（框內為 node name） 閘：主要工作是決定放不放行（唯一的資料變動是裁月份，見節點表）
落地的 catalog 條目（Hive table） MemoryDataset：catalog 沒這個名字，只活在這次 run 的記憶體 production 產物 失敗路徑的終點（沒有東西被寫出去）

只有兩種 config 入圖。inference.products 決定內層迴圈跑幾圈（每個 entity 配幾個 item）， inference.entity_buckets 決定外層迴圈跑幾圈（driver 峰值與落地的分區數）。 inference.snap_dates 這種純過濾條件仍然不畫。
粗虛線邊 = node 自己寫的表（Node(writes=…)），而且它不是拓樸相依邊—— 所以 score_manifest 才要存在，它是唯一保證排名跑在分區寫完之後的東西。 細虛線邊是版本解析的相依（model ⇢ preprocessor）。
SVG 與 .mmd 同步於 #197（2026-08-09）。.mmd 永遠是唯一真實來源； 這頁內嵌的 SVG 是它的渲染結果，渲染步驟見頁末。改了程式碼卻只改 .mmd 沒重渲染， 這頁就會開始說謊——上一次就是這樣落後了三次改動（#185／#187／#188）。

流程圖

來源：docs/diagrams/inference-pipeline.mmd。node 順序以 pipeline.py 的插入順序為準。

三件圖上看得到、只讀程式碼容易漏掉的事

1. node 之間不是傳 DataFrame，是走 Hive round-trip——而 catalog 只擋掉一半

runner 對每個 input 都呼叫 catalog.load()（core/runner.py::Runner.run）。 unranked_predictions 與 ranked_staging 是 Hive managed table，跨月份累積。 catalog 條目有 partition_filter: model_version（#187），所以 load 會發 WHERE model_version = '…' 並把那一欄 drop 掉——但月份沒有任何東西擋。 這就是 rank_predictions 與 validate_predictions 都先呼叫 steps/scoping.restrict_to_snap_dates 的理由：不裁的話第二個月起會讀回全部歷史月份、 重算、無聲重新發布——而重新發布一個沒變的月份，看起來跟正確的一次一模一樣。 圖上標「全表讀回」的那兩條邊就是這件事。

同一個函式的兩種失敗都 raise 而不是放行：inference.snap_dates 為空， 或 frame 裡沒有時間欄。空的 scope 若靜默退化成「全部留下」，正是它存在要防的那件事。

2. ranked_staging 存在的唯一理由是失敗路徑

驗證失敗時 validate_predictions 直接 raise ValidationError，整批中止： production 的 ranked_predictions 完全不被觸碰，失敗批次留在 staging 供事後排查。 publish_predictions 的函式體只有一行 return validated_predictions—— 真正的 production 寫入是 catalog 對這個 node 輸出做的 save。 把紅色那條路徑遮掉，staging → validate → publish 會被讀成三個沒必要的步驟。

3. 模型決定了配哪份前處理，而模型由人決定

inference 預設解析 data/models/best symlink（core/versioning.py::resolve_model_version）， 該 symlink 只能由使用者跑 scripts/promote_model.py 設定——這是整條 pipeline 唯一的人工介入點。 選中的模型再從自己的 manifest 回溯 base_dataset_version，決定要載 data/dataset/<base_dataset_version>/preprocessor.json。 所以 model 與 preprocessor 不是兩個獨立輸入；圖上那條點線就是這個相依。 manifest 缺欄時 CLI 會 warning 並 fallback 到 dataset 的 latest—— 那是舊產物相容機制，不是正式流程（見 inference.md §2）。

怎麼改這張圖

圖的真實來源是 docs/diagrams/inference-pipeline.mmd（Mermaid，純文字）。 這頁內嵌的是它渲染出來的 SVG——改圖請改 .mmd，不要直接動這頁的 SVG，否則兩邊會分岔。

cd docs/diagrams
PUPPETEER_SKIP_DOWNLOAD=1 \

npx -y @mermaid-js/mermaid-cli@10 -t neutral \

兩個實測過的坑：(1) .mmd 裡不要留「只有 %%、後面沒有字」的空註解行—— mermaid 不會把它當註解剝掉，會黏成 %%flowchart 然後報 parse error 在第 1 行，很難聯想；要空行就用真正的空行。 (2) 用 mermaid-cli@10 不要用 @11：v11 的新 renderer 改用 rough.js 畫形狀， 同一張圖會從幾十 KB 灌到數百 KB。
版面上的一個取捨：model 與 preprocessor 刻意不包進 subgraph。 包起來 dagre 會把整個 cluster 當一個整體擺到側邊，主鏈會被拉成右→左→中的鋸齒； 讓這兩個節點自由落在各自消費者的上方，主鏈才是一條可以一路讀下來的直線。
