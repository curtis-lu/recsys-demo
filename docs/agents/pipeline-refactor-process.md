# 一輪 pipeline 重構怎麼跑

給要重整**一整條 pipeline** 的 AI coding agent。本檔回答流程問題：先做哪一步、PR 怎麼切、拿什麼當「行為沒變」的證據、收尾要掃什麼。

**與 [`pipeline-node-design.md`](pipeline-node-design.md) 的分工**：那份回答「重整成什麼形狀」，是形狀判準；本檔回答「怎麼把它跑完」，是流程判準。照著形狀判準改、卻用錯流程，代價是同一件事做兩遍——dataset 就是這樣把結構搬移做了兩遍。

**證據來源**：dataset（PR #162–#180）與 inference（PR #184–#198）兩輪重構的實際軌跡，每條規則都附得出證據的 PR 或 commit。**還沒依形狀判準重整過的只剩 evaluation**（training 已於 #222／#235／#199 那一輪重整），所以這份下一輪還會再用。

> **軌跡在哪**：GitHub 上幾乎沒有 review comment。審查全部是本機 `/code-review` 雙軸 fresh-context subagent，證據在 **PR body** 與 **`fix:`／`review:` 收尾 commit** 的訊息裡（形如「收兩軸審查抓到的 N 件事——最重的是 X」）。

# 一 · 開工順序

## 1. ADR 零程式碼先進 main

先寫下目標形狀，再開始改。

**不照做會發生什麼**：每一次改動都是對的，卻永遠沒有「做完了」這個狀態，而且會做兩遍。ADR-0008 自己記下了這件事——dataset 一帶在 ADR 之前已經改過三次（#152／#159／#162），每次都做對了，但沒有目標形狀。代價是結構搬移做了兩遍（#174 的七檔平鋪 → #176 又移進 `steps/`），ADR-0008 因此被改寫。

**inference 的相反做法**：#184 零程式碼、先於實作進 main，body 寫「讓後續五張票有共同的引用基準」。後續每張票的 body 開頭都引 ADR 章節當設計權威。結果是結構搬移一遍到位（#198），測試斷言一字未改。

**為什麼不是「邊做邊寫」**：邊做邊寫的 ADR 記錄的是已經發生的事，那是變更記錄不是設計權威。設計權威的用途是讓後面五張票不必各自重新決定一次。

**誰擋得住**：沒人。

## 2. ADR 寫錯了要回頭改 ADR，不能只寫在 commit message

ADR 先寫就一定會寫錯——實作時必然發現某條裁決站不住。

**不照做會發生什麼**：**下一個 agent 會照 ADR 把你的 code 改回去。** #183 明訂「衝突時以 ADR 為準」，所以一個只活在 commit message 裡的偏離，對後人是隱形的。#194 因此對 ADR-0010 與 ADR-0011 各補了一則「更正（實作時發現）」，#196 也補了一則。

**為什麼不是「commit message 就夠了」**：commit message 是給讀 git log 的人看的，ADR 是給讀 `docs/adr/` 的 agent 看的。後者才是下一張票會讀的東西。

**規則的完整形式**：票面明訂「衝突時以 ADR 為準」的同時，就必須明訂「偏離要寫回 ADR」。只有前半句，等於要求後人推翻你的實作。

**誰擋得住**：沒人。

## 3. 行為變更先做完，純結構搬移放最後一張

**不照做會發生什麼**：最後一張票沒辦法宣稱「零行為改動」，也就換不到規則 8 那兩樣免費的證據。

inference 的順序是行為全部先（#191–#196）→ 純結構最後（#198）。dataset 把結構夾在中間（#173／#174 → 決策上浮 #175 → 又一次結構 #176），最後那次搬移沒有這個優勢。

**為什麼不是「結構先搬乾淨再改行為」**：結構先搬的話，後面每一張行為票都在動剛搬好的檔，等於把「這個檔沒被動過」這個證明消耗掉。

**誰擋得住**：沒人。

# 二 · PR 怎麼切

## 4. 切點看「這一半有沒有比測試綠更強的證據」，不看行數

- **有** → 切開。合併進下一張票會毀掉那個證明。
- **沒有**（只能靠最終產物比對）→ 不要切。

**兩輪留下的是兩份互相衝突的實例，而衝突本身就是判準：**

**支持切**：#174 的驗收是「29 個 top-level `def`／`class` 一個不多一個不少，除三個 docstring 外 byte-identical」。**這個證明只有在同一個 PR 沒有別的改動時才成立**——合併進 #175（決策上浮）就只剩「測試綠」。

**反對切**：#197 明文否決把 inference 的結構票拆成四段，原話是「blocking edges 是一條直線，而且沒有任何一塊單獨驗收得了——驗收條件是三張表的 digest 與 baseline 一致，那要全部做完才問得出來。一條直線的相依圖是『一個改動的四個階段』而不是『四張票』。」結果 #198 一張票做完結構搬移與決策上浮，測試斷言一字未改。

**為什麼不是「照行數切」**：兩輪最大的三個 PR 裡，#173 與 #198 都是兩千行以上的純搬移，用 AST 逐函式比對把「大」變成可機械驗證的。真正過大的只有 #194——它同時做了新中間表、桶迴圈、逐分區落地、續跑與檢查替換，而那跟行數無關，跟「一票夾幾件事」有關。

**⚠ 這條的信心比其他條低**：它是從兩份衝突實例歸納出來的，沒有任何一份文件明文寫過。

**誰擋得住**：沒人。

## 5. 兩段式 commit：主 commit ＋ 收尾 commit，不要 amend

主 commit ＋ `fix:`／`review:` 收尾 commit。十個 PR 裡有八個是這個形狀。

**不照做會發生什麼**：審查軌跡消失。#192 與 #194 各把審查修正 amend 進主 commit，結果是「這個決定當初為什麼改」在 repo 裡查不到——而在這個 repo 裡，GitHub 上沒有 review comment，收尾 commit 的訊息**就是**唯一的審查記錄。

**為什麼不是「squash 比較乾淨」**：乾淨的代價是把「第一版錯在哪」丟掉，而那正是下一個 agent 最需要知道的事。真實的收尾 commit 長這樣：`b954e862`「收兩軸審查抓到的四件事——含 S2 一個真實的檢查漏洞」。

**誰擋得住**：沒人（但 `git log <branch>` 一眼看得出來）。

# 三 · 機械檢查

## 6. 架構稽核跟搬移放同一個 PR，而且要試「新結構才有的 import 形式」

架構稽核測試要在搬移的**同一個 PR** 加（#174 就是這樣做的）。理由不是紀律，是它會被搬移本身打穿。

**兩次真實的打穿**：

- `b954e862`（同 PR 內審查抓到）：純度檢查只看 import 的 root package，`from recsys_tfb.pipelines.dataset.scoping import _date_filter` 被讀成「import 了 `recsys_tfb`」而放行——**而那正是本 repo 實際在寫的形式**。
- `c712562b`（下一個 PR 自己製造）：解析器只看 `node.module` 不看 `node.names`，`from .steps import scoping` 靜默放行。實測 `pyspark in sys.modules` 為 True 而稽核測試**全綠**。commit 訊息原話：「這個 import 形式只有在有子套件之後才存在，是上一個 commit 親手製造的。」

**規則因此是**：搬檔本身會讓純度／位置檢查變成裝飾品，所以同一個 PR 必須連它一起修，而且 mutation 要下在**新結構特有的 import 形式**上——建了子套件，就要拿 `from .sub import x` 試一次。假綠的形態對照表在 `test-false-green` skill。

**為什麼不是「稽核之後再補」**：補的時候你已經看不見自己製造了什麼新形式了。`c712562b` 就是隔了一個 PR 才發現。

**反向證據**：inference 刻意不新增任何機械約束（#197 的 Out of Scope 明寫「判準全部靠 code review」），改用四軸 fresh-context 審查，#198 一樣過關。**機械檢查不是必要條件，但加了就要當天補洞。**

**誰擋得住**：`tests/test_core/test_architecture_constraints.py`——但它正是會被打穿的那個，所以只算部分。

## 7. 稽核的涵蓋範圍會被搬移悄悄縮小

架構稽核以檔名 glob 掃描（`pipelines/**/nodes*.py`），所以**新建的 `steps/` 子套件不在掃描範圍內**。dataset（#176 起）與 inference（#198 起）都撞到，兩輪都選擇記進文件、放寬 glob 另開票。

**不照做會發生什麼**：你以為稽核在守著新目錄，其實它掃不到。而這個失效沒有任何訊號——測試照樣全綠。

**為什麼不是「順手把 glob 放寬」**：那是獨立的票（#163），而且判準明說不得靠改檔名迴避、也不得新增一條讓自己合規的規則。細節見 [`architecture-constraints.md`](architecture-constraints.md) 與 [`deliberate-non-goals.md`](deliberate-non-goals.md)。**要做先問使用者。**

**誰擋得住**：沒人。

# 四 · 行為沒變的證據

## 8. 驗證手段依 CP 值排序，便宜的先跑

**前四樣免費或秒級，而且抓得到的東西不比實跑少。**

| 手段 | 成本 | 抓得到什麼 |
|---|---|---|
| **mutation（弄壞一行，看紅在哪一行）** | 分鐘級 | 假綠。兩輪幾乎每個 PR 都做，每次 2–13 條 |
| **`git diff main..HEAD -- conf/` 為空** | 免費 | 版本中性＝不重建、不重訓 |
| **`pipeline.py` diff 為空** | 免費 | DAG 與 `--only-node` 可定址性不變 |
| **AST 逐函式比對** | 秒級腳本 | 把「純搬移」從宣稱變成證明：#173 十三個函式逐字相同、#174 二十九個 `def`、#198 十個 helper |
| **同一份 `data/` 的測試 baseline** | 分鐘級 | 分辨「本來就壞」與「被我改壞」 |
| **本機實跑逐列／digest 對照** | Spark cold start 2–4 分 ＋ 一次跑 | **唯一回答「輸出到底變了沒」的東西** |
| **`local_e2e.sh` 末段 assert 逐票累加** | 一次 e2e | 只有實跑看得到的失效（送進去對、存進去錯） |
| **成本驗收量次數不量秒數** | 讀 log | 合成資料的 wall clock 外推不到生產 |

**什麼時候可以不實跑**（#176 立下的明文條件）：零行為改動，而且 `conf/` 與 `pipeline.py` 對 main byte-identical。

**baseline 怎麼建、弄壞驗證怎麼還原**：見 [`known-pitfalls.md`](../operations/known-pitfalls.md) §5 與 §5b。**不要用 `git archive` 拉一份到別的目錄跑**——那份沒有本機 warehouse 狀態，組合跑互擾的那幾項不會出現，會讓人誤以為是自己改出來的。

**為什麼不是「跑實跑最保險」**：實跑一次的成本是 Spark cold start 2–4 分鐘起跳，而它抓不到假綠——一個結構上不可能紅的斷言，實跑也是綠的。

**誰擋得住**：部分。`git diff` 與 AST 比對可機械跑，但沒有東西強迫你跑。

## 9. 輸出本身有雜訊時，先建 noise floor 再比對

模型訓練類的產物（LightGBM、HPO、SHAP 圖、timestamp）**跑兩次就不一樣**，逐列 digest 直接用會得到假陽性。

**作法**（#192 示範過）：先把 main 自己跑兩次跟自己比，記下「本來就會不同」的檔案集合，再拿分支的差異去減。#192 的結論是「差異檔案集合完全相同，branch-only 差異為 0」，而預測表 5,232 列 × 7 欄逐列相同。

**不照做會發生什麼**：你會看到一堆差異，然後花時間逐一排除，最後發現全部都是 run-to-run 的正常抖動。或者更糟——你把真的差異當成抖動放過去。

**為什麼不是「固定隨機種子就好」**：種子固定不了 timestamp、也固定不了 SHAP 圖的繪製細節。noise floor 是把「哪些東西本來就會動」量出來，不是消除它。

**誰擋得住**：沒人。**training 側的重構沒有這一步就證明不了行為不變。**

# 五 · 收尾

## 10. 收尾要 grep 兩份清單：模組路徑 ＋ 符號名

搬移與改名會讓 repo 裡其他東西默默失聯。**兩輪實際發生過九種形態**：

1. ADR／文件指向已刪除的符號或模組（#177 一次收了七處）
2. 文件裡的行號被自己的改動弄過期（三個 PR 各一次）
3. 手維護的流程圖／HTML 落後（#178 漏三條邊 → #182 補；`46b02578` 的 lineage HTML 把遷移前的目錄順序當事實印出）
4. 機械稽核的涵蓋範圍被搬移縮小（見規則 7）
5. log／監控介面靜默改變（#198：十六條 log 的 logger 欄位變了，以 logger 名過濾的監控會靜默失效；十個計時區塊消失，連帶不再發失敗事件）
6. 未進版控的 agent 文件失效（#177：「地雷圖指向不存在的地雷，比沒有地雷圖更糟」）
7. 測試安全網隨著函式一起被刪
8. 本票的驗收條件在下一票撞紅
9. **ADR 自己過時**（見規則 2）

**為什麼是兩份清單**：`c712562b` 抓到舊函式名在四份文件殘留八處，作者自述「**上一輪我只掃了模組路徑、沒掃函式名**」。只掃路徑會漏掉第 1 種形態的一半。

**順帶一條**：引用改寫成**符號名，不要寫行號**（#177 立下的慣例）——行號是第 2 種形態的來源。

**誰擋得住**：沒人。

# 六 · 審查要問什麼

## 11. 有四種錯只有 fresh-context 抓得到

共同點是**作者結構上看不見**，所以「作者再檢查一次」對它們無效：

1. **把 collision 判成「無害的寬鬆」**——作者看到了異常，但沒問「它把兩個不同的輸入映射成同一個結果了嗎」。
2. **宣稱剛好支撐自己已經採取的立場**——`e77e0f70` 作者自述：「我的錯在方法：只查了一個方向就宣稱這個邊界情況不存在，而那個宣稱剛好支撐我已經採取的立場。」
3. **自己上一個 commit 製造的漏洞**（`c712562b`，見規則 6）。
4. **步驟名說謊**——`f5a5b3ad`：註解寫「只有設定的月份可以被抽中」，而那個 helper 在清單為空時回傳整個池。只有實際跑一次判定程序（把 helper 換成機械名重讀 node body）的外部讀者看得到。

**為什麼不是「作者更仔細一點就好」**：這四種的成因都不是不夠仔細，是視角本身被自己的過程遮住了。

**規則的操作形式**：**留一個審查視角不吃驗收條件**，題目是「假設規格本身寫錯了，錯在哪」。全部 prompt 都寫成「逐條對照驗收條件」時，結構上抓不到規格錯誤。派工模板與審查 prompt 的寫法在 `dispatch-subagents` skill。

**誰擋得住**：沒人。

## 12. grep 抓得到的，不要派人讀

死掉的模組路徑、舊符號名、過期的行號——這些是機械題。

**不照做會發生什麼**：浪費 fresh-context 那個視角。它的稀缺性在於「沒被你的過程汙染」，拿去做 grep 做得到的事，等於用最貴的資源解最便宜的問題。

**誰擋得住**：沒人。
