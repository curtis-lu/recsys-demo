# 一輪 pipeline 重構怎麼跑

給要重整一整條 pipeline 的 AI coding agent。本檔回答的是**流程**問題：先做哪一步、PR 怎麼切、拿什麼當「行為沒變」的證據、收尾要掃什麼。

**與 [`pipeline-node-design.md`](pipeline-node-design.md) 的分工**：那份回答「重整成什麼形狀」（node 邊界、body 長相、機制放哪），是判準；本檔回答「怎麼把它跑完」，是流程。兩份都要讀——照著判準改，但用錯流程，代價是同一件事做兩遍。

**這些流程判準的來源**：dataset pipeline（PR #162–#180）與 inference pipeline（PR #184–#198）兩輪重構的實際軌跡。每一條都附得出證據的 PR 或 commit。**還沒依判準重整過的 pipeline 是 training 與 evaluation**，所以這份下一輪就會再用一次。

> **軌跡在哪**：GitHub 上幾乎沒有 review comment。審查全部是本機 `/code-review` 雙軸 fresh-context subagent，證據在 **PR body** 與 **`fix:`／`review:` 收尾 commit** 的訊息裡（形如「收兩軸審查抓到的 N 件事——最重的是 X」）。

---

# 節一 · 一輪的形狀

## P1. ADR 零程式碼先進 main

**先寫下目標形狀，再開始改。** 沒有目標形狀，每一次改動都是對的，卻永遠沒有「做完了」這個狀態。

兩輪的順序相反，代價可量：

| | dataset | inference |
|---|---|---|
| ADR 時點 | 改過三次**之後**才補（#165） | 零程式碼**先於實作**進 main（#184） |
| 後續 | 結構搬移做了兩遍（#174 → #176），ADR 跟著改寫 | 一遍到位（#198），測試斷言一字未改 |

ADR-0008 自己記下了這件事：dataset 一帶已經改過三次，每次都做對了，但沒有目標形狀。#184 的相反做法是「先於實作進 main，讓後續五張票有共同的引用基準」，後續每張票的 body 開頭都引 ADR 章節當設計權威。

## P2. ADR 寫錯了要回頭改 ADR

ADR 先寫就會寫錯——實作時一定會發現某條裁決站不住。

**偏離只記在 commit message 裡是不夠的：下一個 agent 會照 ADR 把你的 code 改回去。** #194 對 ADR-0010／0011 各補了一則「更正（實作時發現）」，#196 也補了一則。這是本流程最容易被跳過、代價卻最隱形的一條。

規則：**票面明訂「衝突時以 ADR 為準」的同時，就必須明訂「偏離要寫回 ADR」。** 只有前半句，等於要求後人推翻你的實作。

## P3. 行為先、純結構最後

inference 的順序是行為變更全部做完（#191–#196）→ 純結構搬移最後一張（#198）。這讓最後那張票可以宣稱「零行為改動」，而零行為改動能換到本檔最便宜的兩樣證據（見 P7）。

dataset 把結構夾在中間（#173／#174 → 決策上浮 #175 → 又一次結構 #176），最後那次結構搬移沒有這個優勢。

# 節二 · PR 怎麼切

## P4. 切點看證據，不看行數

**判準只有一句：這一半有沒有自己的、比「測試綠」更強的驗收證據？**

- **有** → 切開。合併進下一張票會毀掉那個證明。
- **沒有**（只能靠最終產物比對）→ 不要切。

兩輪的證據互相衝突，但衝突本身就是判準：

- **支持切**：#174（結構搬移）的驗收是「29 個 top-level `def`／`class` 一個不多一個不少，除三個 docstring 外 byte-identical」。**這個證明只有在同一個 PR 沒有別的改動時才成立**，合併進 #175 就只剩「測試綠」。
- **反對切**：#197 明文否決把 inference 結構票拆成四段——「blocking edges 是一條直線，而且沒有任何一塊單獨驗收得了……一條直線的相依圖是『一個改動的四個階段』而不是『四張票』。」

**行數不是風險指標。** 兩輪最大的三個 PR 裡，#173 與 #198 都是兩千行以上的純搬移，用 AST 逐函式比對把「大」變成可機械驗證的；真正過大的只有 #194——它同時做了新中間表、桶迴圈、逐分區落地、續跑與檢查替換。

## P5. 兩段式 commit，不要 amend

主 commit ＋ `fix:`／`review:` 收尾 commit。**十個 PR 裡有八個是這個形狀，那是要保留的慣例。**

把審查修正 amend 進主 commit（#192、#194 各一次）會讓審查軌跡消失——而在這個 repo 裡，審查軌跡是唯一能回答「這個決定當初為什麼改」的東西。

# 節三 · 機械檢查何時上

## P6. 跟搬移放同一個 PR，而且 mutation 要下在「新結構才有的形式」上

架構稽核測試要在搬移的**同一個 PR** 加（#174 就是這樣做的）。理由不是紀律，是它會被搬移本身打穿：

- **第一次打穿**（`b954e862`，同 PR 內審查抓到）：純度檢查只看 import 的 root package，`from recsys_tfb.pipelines.dataset.scoping import _date_filter` 被讀成「import 了 `recsys_tfb`」而放行——**而那正是本 repo 實際在寫的形式**。
- **第二次打穿**（`c712562b`，下一個 PR 自己製造）：解析器只看 `node.module` 不看 `node.names`，`from .steps import scoping` 靜默放行。實測 `pyspark in sys.modules` 為 True 而稽核測試**全綠**。commit 訊息原話：「這個 import 形式只有在有子套件之後才存在，是上一個 commit 親手製造的。」

**規則：搬檔本身會讓純度／位置檢查變成裝飾品，所以同一個 PR 必須連它一起修，且 mutation 要下在新結構特有的 import 形式上**（建了子套件 → 就要試 `from .sub import x`）。mutation 的形態對照表在 `test-false-green` skill。

**反向證據**：inference 刻意不新增任何機械約束（#197 的 Out of Scope），改用四軸 fresh-context 審查，#198 一樣過關。**機械檢查不是必要條件，但加了就要當天補洞。**

## P7. 稽核的涵蓋範圍會被搬移縮小

架構稽核以檔名 glob 掃描（`pipelines/**/nodes*.py`），所以**新建的 `steps/` 子套件不在掃描範圍內**。dataset（#176 起）與 inference（#198 起）都撞到，兩輪都選擇記進文件、放寬 glob 另開票。

**不要順手放寬那個 glob**——它是獨立的票（#163），且判準明說「不得靠改檔名迴避，也不得新增一條讓自己合規的規則」。詳見 [`architecture-constraints.md`](architecture-constraints.md) 與 [`deliberate-non-goals.md`](deliberate-non-goals.md)。

# 節四 · 拿什麼當「行為沒變」的證據

## P8. 便宜的先跑，貴的最後跑

依 CP 值排序。**前四樣免費或秒級，而且抓得到的東西不比實跑少。**

| 手段 | 成本 | 抓得到什麼 |
|---|---|---|
| **mutation（弄壞一行，看紅在哪一行）** | 分鐘級 | 假綠。兩輪幾乎每個 PR 都做，每次 2–13 條 |
| **`git diff main..HEAD -- conf/` 為空** | 免費 | 版本中性＝不重建、不重訓 |
| **`pipeline.py` diff 為空** | 免費 | DAG 與 `--only-node` 可定址性不變 |
| **AST 逐函式比對** | 秒級腳本 | 把「純搬移」從宣稱變成證明（#173 十三個函式逐字相同、#174 二十九個 `def`、#198 十個 helper） |
| **同一份 `data/` 的測試 baseline** | 分鐘級 | 分辨「本來就壞」與「被我改壞」。**建法見 [`known-pitfalls.md`](../operations/known-pitfalls.md) §5，不要用 `git archive` 拉到別的目錄** |
| **本機實跑逐列／digest 對照** | Spark cold start 2–4 分 ＋ 一次跑 | **唯一回答「輸出到底變了沒」的東西** |
| **`local_e2e.sh` 末段 assert 逐票累加** | 一次 e2e | 只有實跑看得到的失效（送進去對、存進去錯） |
| **成本驗收量次數不量秒數** | 讀 log | 合成資料的 wall clock 外推不到生產 |

**什麼時候可以不實跑**（#176 立下的明文條件）：零行為改動，而且 `conf/` 與 `pipeline.py` 對 main byte-identical。

## P9. 輸出本身有雜訊時，先建 noise floor

模型訓練類的產物（LightGBM、HPO、SHAP 圖、timestamp）**跑兩次就不一樣**，逐列 digest 直接用會得到假陽性。

作法（#192 示範過）：**先把 main 自己跑兩次跟自己比**，記下「本來就會不同」的檔案集合，再拿分支的差異去減。#192 的結論是「差異檔案集合完全相同，branch-only 差異為 0」，而預測表 5,232 列 × 7 欄逐列相同。

**沒有這一步，訓練側的重構證明不了行為不變。**

# 節五 · 外溢傷害與收尾清掃

## P10. 重構會打斷的東西有九種，掃兩份清單才掃得到

搬移與改名會讓 repo 裡其他東西默默失聯。兩輪實際發生過的形態：

1. ADR／文件指向已刪除的符號或模組（#177 一次收了七處）
2. 文件裡的行號被自己的改動弄過期（三個 PR 各一次）
3. 手維護的流程圖／HTML 落後（#178 漏三條邊 → #182 補；`46b02578` 的 lineage HTML 把遷移前的目錄順序當事實印出）
4. 機械稽核的涵蓋範圍被搬移縮小（見 P7）
5. log／監控介面靜默改變（#198：十六條 log 的 logger 欄位變了，以 logger 名過濾的監控會靜默失效；十個計時區塊消失，連帶不再發失敗事件）
6. 未進版控的 agent 文件失效（#177：「地雷圖指向不存在的地雷，比沒有地雷圖更糟」）
7. 測試安全網隨著函式一起被刪
8. 本票的驗收條件在下一票撞紅
9. **ADR 自己過時**（見 P2）

**清掃要 grep 兩份清單：模組路徑 ＋ 符號名。** `c712562b` 抓到舊函式名在四份文件殘留八處，作者自述「上一輪我只掃了模組路徑、沒掃函式名」。

**引用改寫成符號名，不要寫行號**（#177 立下的慣例）——行號是第 2 種傷害的來源。

# 節六 · 審查要問什麼

## P11. 有四種錯只有 fresh-context 抓得到

共同點是**作者結構上看不見**，所以「作者再檢查一次」對它們無效：

1. **把 collision 判成「無害的寬鬆」**——作者看到了異常，但沒問「它把兩個不同的輸入映射成同一個結果了嗎」。
2. **宣稱剛好支撐自己已經採取的立場**——`e77e0f70` 作者自述：「我的錯在方法：只查了一個方向就宣稱這個邊界情況不存在，而那個宣稱剛好支撐我已經採取的立場。」
3. **自己上一個 commit 製造的漏洞**（`c712562b`，見 P6）。
4. **步驟名說謊**——`f5a5b3ad`：註解寫「只有設定的月份可以被抽中」，而那個 helper 在清單為空時回傳整個池。只有實際跑一次判定程序（把 helper 換成機械名重讀 node body）的外部讀者看得到。

**留一個審查視角不吃驗收條件**，題目是「假設規格本身寫錯了，錯在哪」。全部 prompt 都寫成「逐條對照驗收條件」時，結構上抓不到規格錯誤。派工模板與審查 prompt 的寫法在 `dispatch-subagents` skill。

## P12. 反過來 grep 就抓得到的，不要派人讀

死掉的模組路徑、舊符號名、過期的行號——這些是機械題。派 fresh-context 審查去讀它們是浪費那個視角。

# 節七 · 這份流程的限制

- **每一條都沒有機械檢查**，跟 [`pipeline-node-design.md`](pipeline-node-design.md) 的〈這些規則大多沒人擋得住〉說的是同一件事：能機械化的部分已經在 `architecture-constraints.md`。
- **兩輪的節奏差異（11 個 PR 對 7 個 PR）不能當證據**——inference 的 ADR 與 spec 先在分支上做好，不在 PR 時間軸上。可信的證據是「後面有沒有回頭修」，不是耗時。
- **P4 的綜合判準是歸納出來的**，兩輪留下的是兩份互相衝突的實例，沒有任何一份文件明文寫過這條。用它的時候要知道它的信心比其他條低。
