# Pipeline 效能優化判準

要優化任何一條 pipeline 的效能之前先讀這份。它回答一個問題：**在動手讓某件事變快之前，怎麼確定那件事本來就該做？**

**這份不管「怎麼調 Spark」。** 那是 [`../handbooks/spark-tuning/`](../handbooks/spark-tuning/index.md) 的事——那套手冊教你讀 Spark UI、認 shuffle、調 partition。這份管的是**在打開 Spark UI 之前**該先想清楚的事，因為從執行計畫往上推，會把模型必須做的工當成實作的浪費。兩份都要讀，這份先讀。

**規則從哪來**：2026-09-06 dataset pipeline 的一輪實測（完整紀錄：[`../notes/2026-09-06-dataset-pipeline-profiling.md`](../notes/2026-09-06-dataset-pipeline-profiling.md)）。那一輪提出六個優化假設，**四個被自己的實驗否決**，兩個存活。這份把「為什麼會提出那四個錯的」一般化成判準。每條規則底下都指得出那次的實例。

**這份是跨 pipeline 的。** dataset 只是第一個被量的，training 與 evaluation 的優化適用同一套。

# 一 · 開工前：界定必要工作

## 1. 先確定「什麼是必要的工作」，再問「怎麼算得更快」

**執行計畫告訴你「正在發生什麼」，不告訴你「這是否必要」。** 從計畫往上推，只推得出「也許能省」；從題目往下推，第一個問題就會封死一整片錯誤方向。

推理方向要是這樣：

```
這條 pipeline 是為了解排序問題而存在
        ↓
排序這個目標要求這一步產出什麼？粒度是什麼？
        ↓
那個粒度是誰要求的——模型類別？評估指標？下游契約？
        ↓
（到這裡才）它現在怎麼算的？哪一段不必要？
```

**反例（2026-09-06 實際發生）**：看到 `build_model_input` 的 Spark 計畫裡大表被洗兩次，往上推得出「join 鍵少一個，也許能省一次洗牌」，把它寫成優化候選。從題目往下推的話第一步就會發現：feature 是 `(time, entity)` 粒度，同一個 entity 在同一時點的每個候選 item 看到的特徵本來就一樣；特徵欄被複製到每個候選上，是 flat GBDT 學 entity × item 交互作用的**唯一實作方式**。那不是浪費，是機制。後續三個假設全部建立在這個誤判上，全部實測否決。

**每條 pipeline 該問的具體問題**：

| pipeline | 先問這個 |
|---|---|
| dataset | 輸出框的粒度是誰決定的？（答：模型類別。換 flat GBDT 為 per-item 才會變） |
| training | 這一輪 pass 是誰要求的？資料必須整份在記憶體裡，還是只是現在這樣寫？early stopping 需要看到什麼？ |
| evaluation | 指標是**組內**的還是全域的？組內指標容許哪些群被提前丟掉、哪些聚合能下推？ |

**判斷訊號**：如果你的優化提案講得出「這樣會少算 X」，但講不出「X 對這個題目本來就沒有貢獻」，那你在從機制往上推。

## 2. 優化的前提有**證據等級**，低階的證據撐不起「安全」的宣稱

多數優化都要一個前提才成立——「這裡唯一」「這裡已排序」「這裡不為空」「這個群沒有正例所以不影響指標」。**前提的證據等級決定了優化安不安全**：

```
① 觀察      「我 count 過，這份資料沒有重複」
② 宣告      「config 寫了 max_duplicate_key_ratio: 0.0」
③ 強制      「上游真的對這張表跑過那個檢查」
④ 由建構保證 「bucket 是 split_cols 的函數，同輸入必同輸出」
```

**宣稱「這個優化安全」需要 ③ 或 ④。** ① 只證明「這份樣本剛好如此」，② 只證明「有人寫下了意圖」。

**反例（兩次，同一輪）**：
- 用本機合成資料 `count distinct` 去證明 label_table 在 `(time, entity, item)` 上唯一——那是 ①，只能證明這份合成資料剛好沒重複。
- 退而找到 config 的 `primary_key` ＋ `quality_checks` 宣告，就說「契約守著」——那是 ②。而那條不變量的 docstring 自己寫明了殘留漏洞（兩個鍵一起刪就放行），值可以設成 `0.5` 仍然合法，而且**來源表可能根本不是本 repo 產的**，檢查從未跑過。

**升級證據等級的兩條路**：把檢查搬到使用端（③ → 在真正依賴它的地方斷言），或改寫成不需要那個前提的形式（④ — 那次 `split_train_keys` 的改寫就是：從「distinct + join 湊出同 entity 同一邊」變成「bucket 是函數，所以必然同一邊」，保證從 ① 升到 ④，順便快了 47%）。

## 10. 零成本的淘汰手段先跑完，再花 CPU

**順序**：讀 config → 讀 code → 問使用者一句話 → **最後才**跑實驗。

一個優化假設若能靠前三者淘汰，就不該消耗 CPU 與電力。判斷方式：問「這個假設要成立，
需要哪個 config 鍵是某個值、哪台機器有多少資源？」——那些答案都不用跑實驗。

**反例（2026-09-07 training profiling，完整紀錄：
[`../notes/2026-09-07-training-pipeline-profiling.md`](../notes/2026-09-07-training-pipeline-profiling.md)）**：
該輪提出七個假設，四個是**讀一個檔或問一句話就死**的——「加 `num_threads`」（生產只有
4 核）、「砍 `n_trials`」（20 是搜尋下限）、「val 矩陣磁碟 I/O」（生產有 128 GB）、
「用 gain=0 挑掉特徵」（循環論證：要先跑完一輪才知道刪什麼）。但淘汰它們的順序是
邊做邊發現，中間跑掉了本可省下的實驗。

**特別點名兩種不該花 CPU 的量測**：

- **量常識**。「加核心會變快」不需要量；該量的是「快多少」，而那個數字往往只在
  目標環境量得準（本機的平行效率與生產機不同）。若結論注定是「還是得去生產量」，
  那本機這一輪就是純浪費。
- **量目標環境不允許你動的東西**。動手前先確認這個旋鈕歸誰。見規則 12。

## 11. 沒有目標數字，就不要開始優化

開工前要問到兩個數字：**現在多久**、**降到多少才算成功**。只有前者就沒有停止條件，
會一直往下找，把邊際收益越來越小的東西也做完。

2026-09-07 那輪問了「生產跑多久」（幾小時），沒問「為什麼幾小時是問題、要降到多少」。
結果是在一條 98% 成本由模型本身決定、工程面只剩 10–20% 空間的 pipeline 上，
反覆尋找不存在的槓桿。

## 12. 先確認每個旋鈕歸誰：HPO 在搜的參數不是你的

在有超參數搜尋的 pipeline 上，**能調的旋鈕分成兩類**，動手前先分清楚：

```
HPO 在搜的（conf 的 search_space 裡）   → 值是為了模型品質選的，不是你的
沒被搜、也沒被設的                       → 才是工程可動的範圍
```

**為速度去釘一個 HPO 正在搜的參數，不是優化，是搶 HPO 的工作**——它把成本轉嫁到
模型品質上，而那是建模決策，不是效能工作。

**反例（2026-09-07）**：對 `lgb.train` 做參數消融，量出影響最大的三個因子是
`num_leaves`（−38%）、`feature_fraction`（+18%）、`bagging_fraction`（+4%）——
**三個全在 `conf/base/parameters_training.yaml` 的 `search_space` 裡**。開場讀完那
30 行就會知道消融有一半不用跑。

**做法**：開工前把該 pipeline 的 `search_space` 逐行讀出來，列成「HPO 的／我的」
兩欄。這一步屬於規則 10 的零成本階段。

# 二 · 量測時：尺與實驗

## 3. 先驗證量尺，再相信讀數

在用一把尺量之前，先問「**如果這把尺壞了，我看得出來嗎**」。特別是當讀數剛好符合預期時（見規則 6）。

**反例**：用「在計畫字串裡數 `Exchange` 出現幾次」當量尺，比較 cache 前後。三個變體都數到 10，結論是「repartition + cache 無效」。實際上快取版的 per-join `ENSURE_REQUIREMENTS` exchange **已經消失**，剩下的那個是快取內部的 `REPARTITION_BY_NUM`（物化時跑一次）——字串計數分不出這兩種，把只跑一次的也算成每次都付。差一點得出反向結論。

**常見的壞尺**：
- 計數字串出現次數（分不出巢狀結構、分不出一次性與每次）。
- 只看牆鐘總時間（Spark 是懶的，時間會堆到觸發 action 的那一步，不是做工的那一步）。
- 只看 `func` 不看 `save`（同上，本 repo 的 runner 已經把 load／func／save 拆開，用它）。
- 跨語言邊界用同一把尺（Spark stage 時間 vs driver 端 pandas／LightGBM 時間是兩件事）。
- **在有別人 job 的機器上量**。開場先 `uptime` 看 load、`ps` 看有沒有別的 worktree
  在跑。這台機器常同時有多個 session。2026-09-07 同一組態重複三次量出 61.7／93.6／
  107.7 秒（74% 漂移、單調變慢），根因是另一個 session 中途開了新 worktree 跑 Spark。
  **有漂移時要用配對比較**（變體緊密交錯、每輪對調、比同一輪內的相對值）；未配對的
  區間檢定在有漂移時太保守，會把真訊號判成雜訊。
- **計時器包錯範圍**。下結論前問「這個計時器包住的，是不是我要歸因的那件事」。
  2026-09-07 量 `force_col_wise` 時把 `lgb.Dataset.construct()` 放進計時器，量出
  「省 17%」；那是**建構期**參數，把 construct 移出計時器後差異變成 ±3.5% 且正負號
  在跳（＝雜訊）。同一件事量了三遍才定案。

## 4. 實驗要控制混淆，判準是**區間**不是中位數

- **對調執行順序。** 固定順序會讓後跑的那個吃到熱磁碟快取。
- **重複至少三次。** 單次跑不出區間。
- **判準是區間重不重疊**，不是中位數差幾秒。重疊就不宣稱。

**反例**：四格實驗（兩種 join 順序 × 一個開關）每輪都以固定次序跑，某一格永遠排第三，量出快 4 秒（−17%）。受控重測（每輪對調先後、跑四輪）後兩組區間重疊，差距完全落在雜訊內。

**正例（同一輪，做對的那次）**：先從 Spark 的分區滿足規則推出「這個開關**不該**有效」，把預期寫進腳本 docstring，再設計能推翻它的受控實驗。量出來與預期一致。**先寫預期再量，是防止事後合理化最便宜的手段。**

## 5. 因果確認之前不動現場

根因還是猜測的時候，任何改動都會多一個變數——尤其是改被量測的那份程式。

**反例**：pipeline 在第一個 node 失敗，訊息是「sample_pool 從沒產出這 8 個產品」。我判斷是程式的日期比較有 bug，**動手改了 `nodes.py`**，然後才發現真正原因是這台機器的時區（`Asia/Seoul`）與 Spark session 時區（`Asia/Taipei`）差一小時，`date IN (timestamp)` 恆不成立。程式沒問題。改動後來還原了，但在還原之前，「我量的到底是不是 main 的 code」多了一個不必要的問號。

**特別注意「訊息指錯方向」的失敗**：靜默篩出空集合的錯誤，往往在好幾步之後才炸，而且炸出來的訊息指向完全無關的地方。看到不合理的錯誤訊息，先確認環境（時區、路徑、版本、conf 讀到哪一份），再懷疑程式。

# 三 · 下結論時：自我懷疑

## 6. 支撐既有立場的證據要**加倍查證**，不是放心

當一個發現剛好撐住你前面已經給過的立場，那正是「從結論倒推、找素材撐它」的高風險訊號。**查證強度應該上升，不是下降。**

**反例（同一輪出現兩次，形狀一樣）**：
- 已經宣稱「這是 main 的 bug」→ 就往那個方向找證據，沒去查環境。
- 已經把某條寫成優化候選 → 需要一個前提時，抓了最便宜的確認（count 一下資料），而不是最權威的來源（config 契約與它的漏洞）。

**判斷訊號**：腦中出現「這正好證明我剛才說的」——停下來，去找**能推翻它**的那一個操作。

## 7. 領域通則套用到本專案前，先確認本專案的實際設定

通則是對的，不代表對這個 repo 現在的設定是對的。

**反例**：「零正例的 query group 產生不出 pair，對排序損失的梯度貢獻精確為零，可以砍掉」——這對 lambdarank 成立。但本專案 `conf/base/parameters_training.yaml` 的 `objective` 是 `binary`（pointwise），每一列都進損失，包含零正例群裡的全負例。宣稱之前沒去讀那個鍵。

**做法**：任何依賴「模型在做什麼」的優化，先把它依賴的 config 鍵**逐字讀出來**。`objective`、`metric`、`hpo_objective`、抽樣比例、群定義——這些鍵的值會讓同一條通則的結論反過來。

**連帶**：這也產生一種「改 A 會讓 B 失效」的耦合。若哪天把 `objective` 換成 `lambdarank`，「train 側不過濾零正例群」那個決定就不再正確。**換模型設定時要回頭掃一遍以它為前提的優化。**

# 四 · 交付時

## 8. 設定與程式要分開，**設定的數值不可跨環境搬**

分辨方法只有一個：**改設定、不改 code，看數字動不動。**

```
改 conf → 時間掉  ⇒ 設定層：便宜、可逆、不用寫測試
改 conf → 時間不動 ⇒ 程式層：要動 code、要測試、要驗正確性
```

兩者的交付路徑完全不同，混在一起會讓可逆的那條被不可逆的那條拖住。

**但設定層量出來的數值不可跨環境搬。** 本機是 `local[*]` 單一 JVM（見 [`../operations/dev-setup/local-spark-setup.md`](../operations/dev-setup/local-spark-setup.md)），公司是多 executor 叢集；分區該切多大、記憶體該給多少，是不同尺度的問題。

**能搬的**：診斷方法（看 spill、看每個 task 扛多少）、結論的形狀（「這個 node 的 shuffle 分區偏粗」）。
**不能搬的**：數值本身。

寫進交付物時要明著標，否則下一個人會把本機的值填進生產 config。

## 9. 負面結果要跟正面結果一起留下

被實測否決的假設，跟存活的機會一樣是結果。不寫下來，下一個人（包括三個月後的你）會重走一次——而且會走得更有信心，因為「這看起來明明可行」。

交付物裡要有獨立一節列出：**測了什麼、預期什麼、量到什麼、為什麼否決**。2026-09-06 那份報告的 §6.2 與 §7 就是這一節，佔了那輪一半的工作量。

## 這份規則自己的限制

上面每一條都標了「沒人，只能人看」，那不是敷衍——**這些是推理紀律，寫不成測試**。它們會被違反的時機，正好是當事人自認在做對的事的時候。

所以這份的用法不是「寫完檢查一遍」，是**開工前讀一遍、以及每次要下方向性結論之前回頭看規則 6**。

**已實證的失效方式：寫下來不等於執行。** 2026-09-07 那輪的報告裡確實寫了規則 1 的
那一節（「先確定什麼是必要的工作」），寫完之後整輪仍然由成本斜率表驅動方向——看到
「欄數這一維最貴」就去提砍特徵，而砍特徵是換一個更小的假設空間，屬於建模決策。
**產出漂亮的分析之後，完成感會替代執行。** 對策：把規則 10／12 的「零成本淘汰」與
「旋鈕歸誰」做成開工前的實際動作（讀 config、列兩欄表），不要只當成寫進報告的一節。
