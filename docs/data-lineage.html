recsys_tfb — Data Lineage

全部 Hive 表與主要的 JSON／模型／報表產物的「誰產生、誰消費、長什麼樣」（沒有逐一建卡的 JSON 產物， 例如各項診斷 JSON，見 catalog.yaml）。邊（資料流）對照各 pipeline.py 的節點接線， 各表卡的「下游」以主幹消費者為主，閘門與診斷類節點不保證全列；schema 與型別對照 catalog.yaml / 節點程式碼 / 實際 parquet。範例列：cust_id／snap_date 的值取自本 repo 的合成資料，item 值以 placeholder（prod_A…）示意， 其餘為依 schema 構造的示意列。

recsys_tfb 是通用排序框架，商業銀行產品推薦只是本 repo 的示例。feature_table / sample_pool / label_table / inference_population 這四張來源表是使用者自定義的——框架只規範 schema 的角色欄（time / entity / item / label / score / rank；time、entity、item 由使用者宣告， label、score、rank 框架自帶預設欄名），其餘特徵 / 分群 / carry 欄由應用自定。因此下方表卡 只列角色欄，user 欄位一律以抽象 descriptor 與 placeholder（prod_A、f1…fN、 <enc>）示意，不列舉銀行專屬欄位。示例規模 ~10M 客戶 × 22 產品 × ~1500 特徵 （本 repo 合成版約 1.5 萬客戶月、8 個 item 值）。

Lineage 總覽

階段由上而下：source_etl → dataset → training →（分叉）inference / evaluation。 每個叢集列出具代表性的 catalog 產物（底色 = 版本層；完整清單見 catalog.yaml）。 叢集之間的實線標註實際流動的資料；虛線框是該階段讀取、但由別的階段產出的輸入，框內標明來源。 叢集內的逐表上下游見下方各表卡的「產生 / 下游」（未建卡的產物見 catalog.yaml）。

※ 跨階段的輸入有兩種畫法：別階段產出的主幹產物（model、training_eval_predictions、gain_ledger、ranked_predictions）畫成叢集之間的實線，同時在下游叢集內以虛線框標明來源；其餘來源表與 preprocessor 為避免長跨線，圖上不畫線，只在下游叢集內以虛線框列出輸入與來源。各項的完整流向（含已畫線的 gain_ledger）如下： label_table 同時餵 dataset（組 model_input）與 evaluation（算指標與 baseline；--post-training 的 label 沿用預測自帶的）； feature_table 同時餵 dataset（前處理）與 inference（組評分母體）； sample_pool 除了 dataset（抽樣）之外，在 --post-training 也餵 evaluation（分群母體表）； inference_population 不進 dataset，餵 inference，在預設監控情境也餵 evaluation（分群母體表）； preprocessor 由 dataset 產出，training 與 inference 都讀； training 產的 gain_ledger 在 --post-training 被 evaluation 的 model_capacity 診斷讀。

顆粒度與唯一性總覽

顆粒度＝這張表的一列代表什麼；主鍵用 schema 的角色表達：time（示例 snap_date）、 entity（可多欄，示例 cust_id）、item（示例 prod_name）。 三種標籤：由寫法保證＝由該節點自己的寫入方式使重複不可能、不靠上游（這是唯一的「保證」）； 有檢查＝有直接檢查這張表自己的主鍵有沒有重複、違反會中止的檢查（唯一的近似是來源表：source_etl 查的是 config 宣告的 primary_key，框架不驗它等不等於這張表的主鍵，見下方名詞說明），但不等於一定沒有重複（檢查的位置、時機與範圍見各列）； 框架不檢查＝沒有這種直接檢查，靠上游或使用者自律（可能還有間接的閘，例如只比對列數，見各列）。 標籤描述的是：這張表由框架流程（source_etl 或各 pipeline 的節點）產出時，對它自己的唯一性有沒有直接檢查（被檢查的那組鍵見下方名詞說明）、最弱的一環在哪；使用者不經過該流程、自備的表另計，寫在說明欄。標籤只承認「直接檢查這張表的鍵有沒有重複、違反會中止」的檢查；上游的檢查與只比對列數的閘不繼承。 「某次資料量到沒重複」與「config／文件宣告唯一」也都不算保證。

名詞：本節的「主鍵」是通用說法，指能唯一認出一列的欄位組合；當它等於 time × entity × item 時，就是詞彙表（CONTEXT.md）裡的 identity。source_etl 設定裡的 primary_key 是另一個東西： 那是使用者在 config 宣告、source_etl 用來做重複檢查的鍵，框架不驗它是否等於這張表的 time／entity／item 角色鍵（A32 不看 primary_key 的內容）。 所以標籤看的是「這張表自己的主鍵有沒有被直接檢查」：unranked_predictions 檢查的是 identity；來源表四列的「有檢查」只對「config 宣告的那組鍵」成立（現行四張的宣告與各卡寫的主鍵相同）。

inference_population_features
base_dataset_version		 time × entity（不含 item 展開）(base_dataset_version, time, entity)；partition 另有 entity_bucket 框架不檢查 LEFT JOIN 兩側都沒去重，寫入時沒有直接檢查主鍵唯一的檢查。放大出的重複列因為 entity_bucket 只由 entity 決定，必然落在同一個 chunk（chunk ＝ (time, item, entity_bucket) 分區），所以只要該 chunk 是本次執行寫的，就會被下游 unranked_predictions 的 chunk 檢查攔下；被跳過的 chunk 不重驗。feature coverage 的 log 跑在 join 之前，而且只對 feature 側去重才算，看不到 join 後的放大，不能當證據。
unranked_predictions
model_version		 time × entity × item(model_version, time, entity, item)；partition 另有 entity_bucket 有檢查 predict_and_write_scores 每個 chunk 寫入前由 validate_scored_chunk 跑 no_duplicates，重複即中止。最弱：檢查單位是單一 chunk，不是整張表——只驗本次實際寫的 chunk（分區已存在而被跳過的不重驗），且只看單一 chunk 內，跨 chunk 的重複（例如改過 inference.entity_buckets 後遺留的舊 bucket 分區）這裡看不到。上游 inference_population_features 放大的重複列必落在同一個 chunk（bucket 只由 entity 決定），所以只要該 chunk 是本次執行寫的，就會在這裡被攔下。
ranked_staging
model_version		 time × entity × item(model_version, time, entity, item) 框架不檢查 rank_predictions 先把讀回的表切到本次 inference.snap_dates（unranked_predictions／ranked_staging 這兩張表跨月累積），再去掉 entity_bucket、加上 rank；只會減列、不會增列，也不另做去重。沒有直接檢查主鍵唯一的檢查，本表寫入時也沒有間接的閘：上游 unranked_predictions 的 chunk 檢查不繼承——bucket 被丟掉後，各自在自己 chunk 通過檢查的兩列會合併進同一個 (time, item) 分區；validate_predictions 的間接檢查在本表寫完之後才跑，所以這類重複會先進到 staging，到不到得了 ranked_predictions 見下一列。
ranked_predictions
model_version		 time × entity × item(model_version, time, entity, item) 框架不檢查 沒有直接檢查主鍵唯一的檢查。須通過 validate_predictions 才由 publish_predictions（純轉送）寫入；它有四道 batch check（在 staging 寫完之後、發布之前跑，範圍限本次 inference.snap_dates 的月份），沒有一道是逐鍵的唯一性檢查，但其中三道會間接碰到重複：partition_completeness 比對的是 unranked_predictions 的 chunk 分區，不是本表的分區，缺分區或多出不屬於任何 chunk 的分區（例如改過 inference.entity_buckets 遺留的舊 bucket 分區）就中止，看不到同一分區內部的重複列；completeness 檢查每個 query group 的列數是否等於設定的 item 數；rank_consistency 檢查全表 rank 落在 [1, item 數]（rank 是 row_number()，某群組多一列時最大 rank 會超出範圍）。所以單純多一列會讓 completeness 與 rank_consistency 同時中止；穿得過去的是同一個 query group 內「多一列又剛好少一列」（例如 item A 兩列、item B 零列）。第四道 score_varies_within_group 查同群組分數是否全相同，與重複無關。上游 chunk 檢查與 ranked_staging 一樣不繼承。

來源表的「有檢查」只在 source_etl 產出時成立，而且是寫完之後才查（壞 partition 不回滾），查的是使用者在 config 宣告的 primary_key：dataset／inference 讀取時不重驗，使用者自備、沒經過 source_etl 的表就沒有這一層（例外：label_table 的評估月份仍會被 evaluation 的 prepare_eval_data 重驗）。consistency.py 的 A32 只確認 dataset pipeline 讀的三張表（DATASET_SOURCE_TABLES ＝ sample_pool／label_table／feature_table，inference_population 不在內）在 *_etl 設定裡宣告了 quality_checks.max_duplicate_key_ratio，且值在 [0, 1)；它不看資料，也守不住整個檢查：source_etl 要 primary_key 與這個鍵同時在才會跑，primary_key 被刪時 A32 不會紅；自備表把 *_etl 裡那筆表宣告刪掉時，A32 也直接略過、不報錯。 全表最弱的三處：① 自備來源表——feature_table／label_table／sample_pool／inference_population 這四列的檢查只在「由 source_etl 產出」時成立，而框架明文允許使用者自備來源表（consistency.py 的 B10 段把這件事列為「上游的 max_duplicate_key_ratio 合約關不掉這個洞」的理由之一）。下游有幾道檢查不依賴「來源表由 source_etl 產出」這個前提（自備表也會跑），但各自範圍有限，都不等於全表保證：B10 涵蓋四個 split 的 model_input（test 只比這次組裝的月份），而且只比列數；unranked_predictions 的 chunk no_duplicates 只驗本次執行實際寫的 chunk、只看單一 chunk 內；validate_predictions 的 completeness／rank_consistency 只在 inference 發布前看每個 query group 的列數與 rank 範圍；prepare_eval_data 的 label 重驗只驗 label_table 的評估月份。所以自備 feature_table 有重複時，val／test 的 model_input 不會被這幾道擋下。② model_input 自己的主鍵唯一性沒有直接檢查：train／train_dev 只有 B10 列數閘（只擋右表放大），val／test 連這道間接的閘都沒有；而且 B10 會不會紅取決於重複落在哪個月、以及那個鍵在不在 keys 表裡：落在 train／train_dev 月份、而且那個鍵確實出現在對應的 keys 表裡時，join 會放大列數讓 B10 紅；鍵不在 keys 表裡就不會放大，B10 照樣綠。只落在 val／test 月份時 B10 不會動；這時唯一還會紅的是 prepare_eval_data 的 label 重驗，而且只在該月被列進 evaluation.snap_date 時才發生。B10 也是所有 build 節點落地之後才跑的獨立節點，它紅的時候被放大的表已經寫進 Hive，後續單獨執行或用 --from-node 續跑的節點仍讀得到。③ keys 表（sample_keys／train_keys／train_dev_keys）：只沿用 sample_pool 在 source_etl 產出時的檢查，keys 表本身沒有任何檢查；B10 的列數等式對「keys 自己重複」是盲的（兩邊等量增加），所以這種重複會一路帶到 model_input 都沒有人紅。附註：ranked_staging 寫入時同樣沒有閘，但它的內容在發布前會被 validate_predictions 讀到。

production 由 publish_predictions 寫入，且只在 validate_predictions 通過後才執行：rank_predictions 先寫 ranked_staging，validate 讀它跑 sanity check，失敗即中止、production 不被寫（失敗批次留在 staging 供排查）。ranked_predictions 顯式宣告讓 evaluation 不跑 inference 也能 standalone 讀，避免 MemoryDataset fallback 靜默壞掉。
