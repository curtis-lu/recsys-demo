## 這一章想回答的問題

手冊 01–09 講的都是**還在 Spark 裡**的事：怎麼少搬、少讀、少 shuffle。但很多資料流程有一段
是「Spark 算完 → 收到 driver → 交給 pandas / numpy → 餵進單機模型或報表」。

**這一段是另一個世界，Spark 的所有調校在這裡完全不管用。** 最典型的症狀是：

- `spark.driver.memory` 調到很大，行程還是被殺
- 死法是作業系統的 `Killed`（SIGKILL），不是 Python 的 `MemoryError`
- Spark UI 上什麼都看不到——出事的時候 Spark 根本閒著

原因是 `spark.driver.memory` 管的是 **JVM 的堆積上限**，而 pandas / numpy 跑在**同一個行程的
Python 那一側**。OOM killer 看的是整個行程的 RSS，兩邊加起來。

## 一、numpy 的鐵律：一張矩陣只能有一種格子大小

pandas 的 DataFrame 像試算表——A 欄整數、B 欄小數、C 欄文字都行。numpy 矩陣不行。

它是**一整塊連續的記憶體**，「第 n 格在哪裡」是用 `起點 + n × 格子大小` 算出來的。格子不等寬，
這個算式就壞了。

所以 DataFrame 轉 numpy 時，一定要先決定：**一格要多大，才裝得下所有欄位？**

### 情況 A：全部都是數字

| 欄位型別 | 一個值本來佔多少 |
|---|---|
| float32 | 4 bytes |
| int32 | 4 bytes |
| int64 | 8 bytes |

要找一個「都裝得下、又不失真」的格子：整數最大要 8 bytes，小數要能表示小數點——最小的共同解
是 **8 bytes 的 float64**。

注意代價：原本只要 4 bytes 的 float32 欄，也會被撐成 8 bytes。這是「一格一種大小」的稅。

### 情況 B：混進了一欄文字

**沒有任何固定寬度的格子能同時裝下 `3.14` 和 `"信用卡"`。**

numpy 只剩最後一招：格子裡不放東西本身，改放一個 8 bytes 的**記憶體地址**，指向真正的東西擺在
哪裡。這種格子叫 `object`。

```
情況 A（數字矩陣）              情況 B（地址矩陣）
┌──────┬──────┬──────┐        ┌──────┬──────┬──────┐
│ 3.14 │ 42   │ 7.0  │        │ #001 │ #002 │ #003 │  ← 每格只是櫃號（8 bytes）
├──────┼──────┼──────┤        ├──────┼──────┼──────┤
│ 2.71 │ 13   │ 9.5  │        │ #004 │ #005 │ #006 │
└──────┴──────┴──────┘        └──────┴──────┴──────┘
   數字就在格子裡                    ↓ 數字全在別的地方
                                置物櫃 #001: [外殼 24B] 3.14
                                置物櫃 #002: [外殼 32B] 42
                                置物櫃 #003: [外殼 24B] 7.0
```

**關鍵在「外殼」。** 為了讓一個數字能被地址指到，Python 必須替它做一個獨立的小物件；這個物件
除了數字本身，還要背一層 **24–32 bytes** 的管理開銷（型別是什麼、有幾個地方正在用它）。

每一格的成本因此變成：

```
8 bytes（櫃號）+ 24~32 bytes（櫃子外殼）≈ 34 bytes
```

**一欄文字，就讓另外幾百欄的數字全部付出四倍代價。** 那幾百欄裡的每一個數字，都必須離開原本
緊密排好的隊伍，各自搬進一個獨立的櫃子。

這就是為什麼「只是多了一欄字串」會讓記憶體從 20 GiB 變成 90 GiB 級。

## 二、怎麼實測每格的真實成本

不要用推算，實測。方法：

1. 取一個**小樣本**（例如 10 萬列），但**欄位型別比例要照真實資料**（幾欄 float32、幾欄 int32、
   幾欄 int64）。每格成本與列數無關，所以小樣本可靠外推。
2. **整數值要刻意避開 −5..256**。CPython 對這個範圍的小整數有物件快取，共用同一個物件、不各自
   配置外殼——用小整數量會嚴重低估成本。
3. 量真實的 RSS（`psutil` 或 `/proc/self/status` 的 `VmRSS`），**不要用 `ndarray.nbytes`**（原因見
   下一節）。
4. 除以格數，得到「每格 bytes」。

拆解對帳（讓數字可驗證，不是黑箱）：

```
櫃號（指標）                          8.0
401/663 欄 × 24B（Python 小數物件）  14.5
 92/663 欄 × 32B（Python 整數物件）   4.4
162/663 欄 × 32B（Python 整數物件）   7.8
文字欄本身                             0    ← 字串物件與來源 DataFrame 共用，不重複配置
                                    ─────
                                    34.7    （實測 34.2）
```

推導值與實測值只差 1.4%，代表這個模型是對的。**做這種對帳的價值不在數字本身，在於它讓你知道
自己有沒有漏算一項。**

## 三、三個會咬人的邊界

### 3.1 `nbytes` 會說謊——觀測性在這裡是瞎的

大部分「記錄矩陣多大」的工具問的是 numpy 自己：

```python
X.nbytes   # 或 sys.getsizeof(X)
```

**numpy 只算櫃號，不算櫃子。** 對 `object` 矩陣，它回報的是 `格數 × 8 bytes`——完全不含那 30 億
個外殼。

實測中，同樣 10 萬列，object 矩陣與 float64 矩陣回報的數字**完全一樣**（皆 0.49 GiB），但真實
記憶體差 **4.3 倍**。

**不要用這個數字判斷記憶體是否安全。** 這是最陰險的一點：你的監控是綠的，行程照樣被殺。

### 3.2 就算記憶體無限大，這條路也走不通

`object` 矩陣不只是慢和肥，它**根本不合法**。多數單機模型庫（LightGBM、XGBoost、sklearn）拿到
非 float32/float64 的輸入會一律嘗試轉型：

```python
np.asarray(mat, dtype=np.float32)
```

碰到那幾格真的是 `"信用卡"` 的：

```
ValueError: could not convert string to float
```

**記憶體不足只是先發生的症狀。真正的病是文字欄混進了數值欄。** 這件事值得單獨記住，因為它決定
了修法方向：不是加記憶體，是把型別修對。

### 3.3 pandas 轉 numpy 時有一份看不見的暫態

pandas 拼出最終矩陣時，是**一個型別群組一個型別群組**地填。填 `object` 矩陣時，每個群組都要先
整批做成櫃號陣列。

最大的那個群組（例如 401 個 float32 欄 × 450 萬列）會產生一個
`401 × 4,542,746 × 8 bytes ≈ 13.6 GiB` 的臨時陣列。

填 `float64` 矩陣則不需要這個中介。

**所以估算峰值時，光算「來源 DataFrame + 目標矩陣」會低估。** 至少還要加一份最大 dtype 群組的
暫態。

## 四、降低 Spark → pandas → numpy → 模型 峰值的手法光譜

由低成本到高成本。前兩項幾乎必做，後面依需求往下走：

| 做法 | 動到什麼 | 代價與風險 |
|---|---|---|
| 把非數值欄從特徵集移除（編碼或丟棄） | config | 無；這是把 `object` 矩陣打回 `float64` 的唯一辦法 |
| 提早釋放來源 DataFrame、拿掉多餘的 `.copy()` | 取值順序 | 無；pandas ≥1.4 的 `df[cols]` 已回傳獨立副本，再 `.copy()` 是白付一份 |
| 矩陣改用 4 bytes 格子（`to_numpy(dtype=np.float32)`） | 一行 | ⚠ **int64 欄若有值 > 2²⁴ 會失真**，套用前必須驗值域 |
| 讓模型庫直接讀 Arrow，不經過 pandas / numpy | 資料交接方式 | 需要 `cffi`（**不是** pyarrow 或 lightgbm 的相依套件，生產環境未必有） |
| 一次只讀一小段、邊讀邊餵（`lightgbm.Sequence` 之類的串流介面） | 約 25 行自寫 adapter | 只需 numpy；峰值可壓到「分箱後的資料集本身」那個下限 |

最後一列的下限值得記住：**串流讀入之後，剩下的就是模型自己要存的那份**（LightGBM 是分箱後的
`train.bin`）。那是跑不掉的底線，再優化也降不下去。
